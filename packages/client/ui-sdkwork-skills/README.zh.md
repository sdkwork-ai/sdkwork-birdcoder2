# @deepseek-ai/dsh-client-ui-sdkwork-skills

[English](README.md) | 中文

## 摘要

技能管理在设置面板中新增一页——「技能」，位置在「模型」与「插件」之间——并由一份宿主真正执行的持久化偏好支撑。该页列出当前组合实际提供的技能目录：已打开会话时是会话自身的视图，未打开会话时则是组合级清单（内置 / 预设 / 用户级根）。它按新建会话技能标签条使用的同一套场景分组（代码开发 / 媒体创作 / 文档生成，其余归入一个「其他技能」桶），并为每个技能提供启用开关、推荐标签开关，以及承载目录自带事实的详情展开。被停用的技能对目录而言不再存在：「/」菜单不再提供它，面向模型的目录也不再宣传它，而磁盘上的技能文件从不被改动。推荐标签开关是标签条成员关系的加法半边：它既能移除用户不需要的场景表座位，也能为一个场景表从未有过座位的技能加上座位，而该页无需知道自己在做两件事中的哪一件。

## 对外表面

三处贡献，正好对应本功能需要跨越的三层：

- **技能页** —— 浏览器半边注册一个 `settings.section`（id 为 `skills`，order 12，标题取自本包字典）。设置外壳把它渲染在内容列并补上导航行；外壳完全不知道「技能」是什么。该页渲染按场景分组的目录行，配有可同时匹配名称、描述、来源文案、提供方与中文别名的搜索框、每个分组的「全部启用 / 全部停用」，以及五种被如实区分的状态：准备中、加载中、加载失败（带重试）、组合级清单（并如实标注为组合级）、搜索无结果。
- **停用提供者** —— 宿主半边注册一个 rank 为 0 的目录提供者 `sdkwork-skill-suppression`，把每个被停用的名字以 `modelInvocable: false`、`userInvocable: false` 重新上架。原理见[停用如何真正生效](#how-a-disabled-skill-disappears)。
- **`skillPreferences` 服务** —— 浏览器半边把设置段投影成一个跨插件只读面（`getSnapshot` / `subscribe`）。特性插件不得运行时导入另一个特性插件的值，因此这是消费者——新建会话技能标签条——得知用户把哪些技能移出推荐行的唯一途径。消费者通过 `ctx.get('skillPreferences')` 获取，并容忍其不存在。

## 配置

本插件拥有一个设置命名空间 `ui-sdkwork-skills`，由宿主半边注册、浏览器半边绑定。三个字段都是名字列表：

| 字段 | 含义 |
|---|---|
| `disabledSkills` | 宿主从其提供的每个目录中抑制掉的技能。 |
| `hiddenSceneTags` | 从新建会话技能标签条中移除、但完全可用的技能。 |
| `pinnedSceneTags` | 加入新建会话技能标签条、且完全可用的技能。 |

三个列表里都没有的名字，表示用户从未动过该技能，因此清空某个字段——或整段——即回到组合默认值。持久值存放在宿主用户设置文档中，这意味着该设置跨重启保留、且按用户而非按项目生效；而它所过滤的目录是按项目生效的。

### 为什么需要两份标签列表而不是一份

`hiddenSceneTags` 与 `pinnedSceneTags` 表达相反的方向，而该页写入的是与名字**场景默认值**相符的那一份，而不是每次固定写同一个字段。原因在于场景表是 `ui-sdkwork-app-modes` 拥有的构建期产品决策：它为自己的每个技能提供默认座位，而纯减法模型只能把这些座位拿掉。一个本无场景表座位的技能——`dsh-*` 包、预设 `customSkillDirs` 条目、用户级技能——将永远无法被推荐。加入第二份列表把成员关系变成 `场景表 − hidden + pinned`，这正是让该页**每一行**都带上可用开关、而不只是场景表恰好挑中的那几个的原因。

两份列表刻意**不**约束为互斥，store 也不强制其互斥：较早的文档、手工编辑，或两次写入之间的竞态，都可能让同一个名字出现在两边。此时**hide 胜**——`hiddenSceneTags` 中的名字无论是否在 `pinnedSceneTags` 中都绝不渲染标签。该优先级只在**一处**计算（`skillPreferences` 的 `hidden` 集合），由标签条逐标签消费，因此不存在第二份实现可供漂移。

该页的开关刻意做成方向中立的：它渲染「显示 / 不显示」，并把自己的场景表成员关系作为 `sceneDefault` 参数向下传递，由写入路径用它来选择字段。因此把某个场景表技能重新打开，会**清掉**它的 `hiddenSceneTags` 条目而不是添加一枚冗余 pin；把某个无座位技能关掉，会**清掉**它的 pin 而不是添加一条冗余 hide。存储段由此保持无死条目，且每次写入都是纯设置写入——从不是对一个反向标志取反。

## 停用如何真正生效

停用是「注册一个提供者」，而不是「加一层过滤器」，因为过滤器得在每个消费点各写一遍。技能注册表按层合并候选，候选的 `rank` 决定同一层内同名者谁胜出：

| rank | 来源根 |
|---|---|
| 100 | 项目 `.dsh/skills` |
| 200 | 项目 `.agents/skills`（全部 BirdCoder 内置技能） |
| 250 | 运行时注册 |
| 300 | 自定义目录 |
| 400 / 500 | 用户级根 |
| 600 | 内置（bundled）根 |

停用提供者的 rank 为 0，无需给任何上游文件打补丁即可赢下所有同名比较。它的候选带着同时隐藏两侧的调用策略，而两侧各自在自己的边界上过滤，而不是由宿主替它们预过滤：`/` 菜单处理器按 `isUserInvocable` 过滤，面向模型的目录按 `modelInvocable` 过滤。这个分工是刻意的——它让 `skills.list` 保持为一份**中立清单**，本页因此能列出并开关一切，包括只有模型可调用的技能。选择「抑制」而非「删除」还意味着技能文件仍然待在用户（或仓库）放它的位置，重新启用只是一次纯设置写入。

提供者在每次 `list()` 调用时读取设置段，因此答案永不陈旧；注册表会缓存已完成的目录，这正是设置提交还必须通过该提供者注册自带的 control 触发失效的原因。

### 会话目录与组合级目录

`skills.list` 是双寻址的。给定 `sessionId` 时，它照旧回答该会话自身的项目级目录。改为给定 `scope: 'all'` 时，它回答组合级清单：所有不依赖工作目录的根。机制就是注册表自身的根选择——没有 `cwd` 时项目根被跳过，而自定义、用户级与内置根仍会挂载——因此全局视图并非在手工拼出的路径列表上另开一条代码路径，而是同一个注册表回答一个它本就能回答的问题。这正是该页在工作区尚未选定前仍有用的原因，而该页会说明自己显示的是两者中的哪一种，不会假装这份列表是项目级的。

## 与新建会话技能标签条的关系

输入框下方的标签条（`ui-sdkwork-app-modes`）把其场景的技能渲染为推荐标签。它订阅 `skillPreferences` 并应用两份列表：`hiddenSceneTags` 中的名字被丢弃，`pinnedSceneTags` 中的名字被追加，同时在两边的名字按隐藏处理；整个场景的标签都被隐藏时，标签条不渲染任何内容，而不是渲染一个空行。这些设置在力度上刻意不同：两份标签列表只改变「推荐什么」，`disabledSkills` 改变「什么存在」。未组合本插件的部署会显示场景表自带的全部标签——这里的注入是可选的，标签条自身的 fiber 永远不会因它而等待。

**运行时不变量：** 不发布 companion。停用集合是具名设置段落的纯投影——提供者在每次 `list()` 调用时重读它——因此唯一可能漂移的状态是注册表「已完成目录」缓存，而设置提交会通过注册自身自带 control 使其失效。手工编辑的设置文档同样无法破坏技能发现：不满足注册表名字语法的名字在成为候选之前就被丢弃，非列表字段则读作「什么都没抑制」。这两条性质由宿主测试断言，而不是由一个运行时 companion 观测。

## 已知限制与后续工作

- **`disabledSkills` 按用户，而非按项目。** 它对该用户打开的每个项目生效。若要做按项目的覆盖，需要让设置段以项目根为键。
- **组合级视图是按组合，而非按最近项目。** 无会话时该页显示不依赖工作区的根；它刻意不为用户尚未打开的项目臆造一个 cwd。
- **目录两侧与标签条都按用户。** `hiddenSceneTags` 与 `pinnedSceneTags` 是对整个用户的一套集合，而不是每个场景一套。在代码场景暂存时隐藏的技能，在媒体场景下同样隐藏。
- **技能消失后其 pin 仍会在标签条上渲染。** 标签条仅凭偏好列表追加 pin，不拿它去校验已获取的目录，因此被移除的技能留下的 pin 会显示为一枚死标签，直到在本页清掉它。本页只列出宿主确实提供的名字，陈旧条目正是在这里可见、可删。
- **模型仍会在其提示历史中看到该名字。** 会话中途停用的技能会在下一次目录读取时消失，但已经组装好的那一轮已经组装好了。
- **不能编辑技能自身的元数据。** 描述、`whenToUse` 以及模型/用户可调用策略由技能文件的 frontmatter 拥有；该页只展示它们，从不写入它们。

## 开发说明

`pnpm exec tsc -b packages/client/ui-sdkwork-skills/tsconfig.host.json` 单独对宿主半边做类型检查，`pnpm exec tsc -b packages/client/ui-sdkwork-skills/tsconfig.client.json` 检查浏览器半边；本包之所以拆成两个面，是因为两侧会在同一批键上合并 cordis `Context`，没有任何单一程序能同时看到两边。它参与的全仓门禁是 `tsconfig.host.json`（宿主半边及其测试）与 `tsconfig.client.tests.json`（浏览器半边测试），外加 `pnpm run verify-builtin-scene-skills`——后者保证本页场景表与输入框标签表始终与打包技能保持一致。页面组件测试直接驱动 store，宿主测试则在真实 Cordis 上下文里、用替身 `settings` 与 `skills` 服务驱动提供者。

给下一位改动 Remote 契约的人一条提示：本页的 `SkillCatalogSource` 联合与宿主的 `SkillEntrySource` 联合，是同一套闭合词表（`project` / `custom` / `user` / `bundled` / `runtime` / `unknown`）的两种拼写——宿主在 `skills.list` 边界把注册表开放的 `source` 字符串收敛进这个闭合集合，客户端 store 为避免导入宿主类型而重新声明一份。若将来新增来源类别，两处拼写与成对的 `row.source.*` 字典条目必须一起改动——宿主测试的来源映射用例会最先变红。
