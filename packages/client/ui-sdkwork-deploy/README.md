# @deepseek-ai/dsh-client-ui-sdkwork-deploy

English | [中文](README.zh.md)

## Summary

The session-header rocket opens the app library: a bounded workspace scan discovers every project carrying `agent.app.config.json` and lists it with its manifest name, type, icon and linkage state. Each row publishes, uploads code to, or builds that project; the footer creates a new app through the console's full form; an empty scan renders a clickable placeholder with the same action. Creation writes a complete APP_MANIFEST_SPEC v3 manifest — identity, per-type runtime, publish, media and linkage — and the library re-scans live as the session cwd moves.

The settings-menu popover's 我的应用 row opens a two-tab read-only drawer. 我的应用 lists the caller's own `deploy_app` rows (the app API's `USER` ownership scope), newest first, narrowed by an application-kind facet; 我的应用模板 lists the caller's own template listings (`template.appTemplates.list`, already account-scoped), newest first, narrowed by a listing-status facet and annotated with each listing's latest semantic version and install count. Both tabs read the same host-constructed clients as the publish flows and never write.

The row menus expose **two independent template dialogs**. 发布为模板 opens the publish dialog; 从模板安装 opens the install dialog. They share only the modal frame and design tokens — neither imports the other's flow, state, or panel. The publish dialog has two sources. The default scans `<project>/apps` for the independent application roots the SDKWork workspace standard defines (`apps/README.md` index + `agent.app.config.json`) and lets the operator select exactly one. The second picks one arbitrary directory through the Host directory picker; the detector reads its markers and `package.json`/`pubspec.yaml` (governed manifest first, then Flutter, React Native/Expo, Android, iOS, HarmonyOS, mini program, Electron/Tauri, web frameworks, static HTML, server frameworks) and proposes an application type that the operator can override before publishing. Both sources create one development scaffold template: the app is matched to the caller's own platform app (or registered from the detected/manifest type), the directory is read through the Host bridge, zipped **locally** with the `.gitignore`-aware fflate packer (sensitive files excluded), and only that zip is uploaded as the version artifact; the listing is then created — or updated with a new version when the same account already owns a template for that platform app and key. The surface is a two-stage wizard — choose one app root or custom directory, then confirm its store listing and shared settings with the single publish run shown inline — so the common case never becomes a batch form. The flow is four focused steps: **choose one app**, **Store assets** (square logo, 16:9 cover, up to eight ordered sample pages), **Basic information** (name, key, subtitle, long description) and **Version and publish** (version, changelog, category, visibility, review submission and a publish summary). Every step after the first shows a compact selected-app context bar and a single centered form column; the primary action never scrolls away and the final step owns publish/result. Images are previewed locally, validated by type/size/count, uploaded to Drive after the platform app exists, and persisted as stable `drive://` refs (`iconMediaRef`, `coverMediaRef`, and `metadata.screenshots`); existing refs survive when no replacement file is chosen. The selected app carries its name, key, version, changelog, live progress (including media upload and local-zip stages), and a failed run can be retried. The separate install dialog lists the caller's templates (and the marketplace) and installs one into `<project>/apps/<template-key>` — appending a numeric suffix instead of overwriting an existing local app — or into a custom absolute directory; after the files land it records the template identity in the installed manifest and upserts the app's row in `apps/README.md`.

## Use this package

Mount this plugin alongside the runtime (one cordis.yml row plus a dependency on this package). The header icon opens the app library popup; the row-menu publish entry runs the per-project flow against the row's own directory.

**App library (header trigger).** The popup scans the session cwd (depth 3, at most 120 listed directories, pruning hidden and build-output children) for `agent.app.config.json` manifests and lists every project it finds:

- Each row shows the manifest's display name, derived type label (the console type card the manifest maps to), linkage badge, project path, and logo (`app.iconUrl` / `media.icons.primary.url`, falling back to the name's initial).
- The row's right side runs 发布 and 上传代码 through the shared project flow for that directory (creating or linking first when the manifest records no app), 打包 through the host build port's progress dialog when the composition ships `sdkwork-app-build`, and 源码 through the source binding dialog: the two source forms an app carries beside its deployment code.
- The file walk merges with the caller's deploy apps: an owned app no local manifest references — a creation that had no session directory to host a manifest, a failed linkage write, or a session project already recording another app — lists as a server row with the **未关联本地目录** badge and opens publish/upload directly (no build action, since there is no directory to build). A successful creation is therefore never invisible: the popup shows it whether or not a manifest landed.
- An empty merge renders a clickable placeholder whose action is the footer's 新建应用: the console's full create form, whose type grid covers the whole SDKWork app vocabulary (h5, pc-web, desktop, mini-program, android, ios, harmonyos, api-service, static-web, each with its framework stacks). A freshly created app is linked to the session project when that project records no app yet.

**My apps (settings menu).** The `我的应用` row opens a read-only two-tab drawer over what the account deployed; the view switch sits above the active ledger. Each ledger mounts on its first visit and stays mounted while its tab is inactive — hidden from the accessibility tree, so `aria-controls` on both tabs resolves — which keeps its rows, facet selection and resolved versions across a switch. Closing the drawer resets the view to 我的应用, so reopening reads only that ledger.

- **我的应用** lists the caller's own `deploy_app` rows. The listing is `apps.list` under the `USER` ownership scope — the server's ownership gate still decides reachability, and the scope only narrows it to the caller's personal apps. Every page is loaded first (100 rows per request, a five-page ceiling reported as a truncation note) so the application-kind chips and the rows they filter come from the same set; an empty chip selection means "all kinds", while selection is OR. Rows show the app name, slug, kind, status, latest release tag and update time, newest first.
- **我的应用模板** lists the caller's own template listings through `template.appTemplates.list` (account-scoped by the API). The same paging and status-facet rules apply, with the five listing statuses as chips in publish-first order. Each row shows the template name, key, summary, status, latest semantic version and install count, newest first. The version is a side read: the listing's own `version` field is an optimistic-lock counter, so the tab resolves the latest version page per listing and shows nothing when that read fails, keeping the row visible.
- The drawer also carries refresh/retry, per-tab loading placeholders, empty and filtered-empty states, a truncation note, an unconfigured-gateway notice, and the shared sign-in prompt while signed out. It writes nothing: publishing and installing stay on the app library, the row menus, and the template center.

**Row-menu project flow.** One flow serves every entry, driven by the project's manifest state:

- **No recorded app**: 创建应用并发布. The manifest supplies the draft (display name, type card derived from `appType` / `runtime` / `publish.platforms`, description, app key); the confirmation creates the app, or hands off to the console's full create form when the manifest cannot determine a type card.
- **Recorded app that resolves**: 发布应用 and 上传代码. The flow re-reads the manifest immediately before creating, so a project that acquired an app in another window cannot be given a second one.
- **Recorded app that no longer resolves**: replacement creation that rewrites the same linkage entry.
- **发布为模板** and **从模板安装** are independent row-menu actions (`deployPublish.openPublishTemplate` / `openInstallTemplate`): the first opens the publish-only dialog, where one of the project's independent `apps/` roots is selected with its dedupe state, or one arbitrary directory is picked and type-detected, and a select → configure/publish wizard drives the single run; the second opens the separate install dialog, where one template installs back into `apps/` or a custom directory. The header popup stays the app inventory, not a second menu.

**Creation writes a complete manifest (APP_MANIFEST_SPEC v3).** When the target project records no `agent.app.config.json`, the linkage write composes the full skeleton instead of the linkage-only stub the standard's §4.1 permits: every required section (`app`, `backend`, `runtime`, `media`, `publish`, `artifacts`, `release`, `security`), the identity the created record carries (key derived from the governed key, the name's kebab, or the console slug; name, display name, description, `appType`), the runtime identity the spec's §6.1 client-architecture alignment assigns to the app's type card or kind (family, framework, `publish.platforms`, `supportedDeploymentProfiles` + default `standalone`), the product icon at both icon slots when the create form uploaded one, the canonical `metadata.deploymentConfig` pointer, and the initial `0.1.0` release entry. Fields the creation flow cannot truthfully know — official website, screenshots, the package matrix — stay absent for the app repo's authoring pass; nothing is fabricated. An existing manifest is only merged, never rewritten. Reading a composed manifest back resolves the same type card again, and with the record's icon and website supplied the composed manifests pass `check-app-manifest-standard.mjs` for all nine cards.

**Source binding.** The 源码 action opens the source binding dialog over the row's project: **本地目录** picks a directory and records it as `metadata.publishing.birdcoder.sourceDirectory` (what 打包 builds and the publish dialog defaults to); **Git 仓库** records an https clone URL, optional default branch, and the project subdirectory the app packages (`sourceGitUrl` / `sourceGitBranch` / `sourceSubDirectory`), and when the manifest records a linked app the binding also lands on the platform through the publishing service's `connectGitSource` (`sourceRepositories`). A project without a linked app records the manifest spec only and binds at its first publish or creation. The row carries a 源码：本地目录 / 源码：Git badge while either fact is recorded, and the dialog opens prefilled from the manifest.

**Live list.** The library re-scans when a stacked surface closes and on every change the host channel carries while no surface is stacked — a session cwd move, or another surface's manifest write (the row-menu flow forwards its outcomes as host notifications) — so creation, linkage, and session switches reflect in the window without reopening.

The canonical linkage lives in the app manifest (APP_MANIFEST_SPEC §4.1): `metadata.publishing.appIdByTarget[<mode>.<environment>]` holds the platform app id, and `metadata.publishing.birdcoder` beside it records the fork-owned display and template provenance. The deployment profile key is the manifest's `runtime.defaultDeploymentProfile` plus the host's active lifecycle tier (`testing` maps to `test`). Earlier plugin versions wrote a top-level `deploy` section and overwrote `backend.appId`; reads still accept the legacy section, and the first write folds it into the canonical block and removes the unknown top-level key. The IAM application id in `backend.appId` is left untouched.

Creation is one operation with three persisted facts, in order: the `deploy_app` record, the project linkage, then the platform target for the manifest's type card. A failed linkage write keeps the created app and offers **重试写入项目关联**, so a retry can never register a second app. When the manifest cannot determine a type card (an ambiguous mobile root, or no manifest at all), the confirmation hands off to the console's full create form.

### Runtime invariants

No runtime invariant companion is published; this package is a UI plugin whose session-header entry only opens the shared publish flow. It owns no cross-plugin mutable state, and its single slot registration proves disposal through the HMR-safety spec.

## Model Experience

None, as the plugin renders human-facing publishing dialogs and writes deployment records and the project manifest; it adds no prompt content, tools, or session events.

#### KV Cache effect

None; SDKWork deployment requests and manifest writes are separate browser traffic and do not alter Harness provider requests.

## Known Limitations and Deferred Work

- A composed manifest fills only what the creation flow truthfully knows. `app.officialWebsiteUrl` and the primary icon (when the create form uploaded none) stay absent, so the canonical `check-app-manifest-standard.mjs` reports exactly those two fields until the app repo's authoring pass fills them; screenshots and the package matrix are likewise deferred. Nothing is fabricated.
- The server merge fetches the caller's apps with the picker's page size (50); an operator owning more apps than the cap sees the rest in the deployments console.
- The settings-menu 我的应用 drawer walks at most five pages of 100 rows per tab and says so when the ceiling bites; a caller owning more apps or templates than that reads the rest in the deployments console.
- The 我的应用模板 tab resolves each listing's latest semantic version with one version-page read per listing, at most four in flight; the rows render before those reads start. A failed or empty version read leaves that row without a version number rather than hiding or failing the row, and a listing with no `latestVersionUuid` makes no version request at all.
- Neither tab offers search: both sets are bounded by the page ceiling and filtered locally by their facet chips. The view switch carries no per-tab counts, so learning whether the other ledger has content takes opening it. The view resets to 我的应用 on close; a mounted ledger keeps its facet selection only while the drawer stays open.
- The templates tab points publishing at the project row menu's 发布为模板 action and does not install templates itself: installing needs a project directory and a target choice, which the separate install dialog already owns.
- Custom-directory type detection is a marker/package heuristic. A monorepo root, several frameworks in one directory, or an uncommon layout can be misclassified; the type select is the correction path and an untyped candidate cannot advance.
- A custom directory without `agent.app.config.json` is published without writing an app/template linkage; the UI warns before publishing and the account-scoped template key still dedupes the next run.
- The local zip is assembled in renderer memory. The same 2 GiB generic package cap, 20,000-file/24-level listing bound, and 64-path/32 MiB read batches as an `apps/` root apply, so a very large custom directory is refused rather than streamed.
- The library scan is a bounded walk (depth 3, 120 listed directories, 300 listing attempts, hidden and build-output children pruned) driven by the workspace listing bridge, which cannot distinguish files from directories; a file child costs one failed listing. A project nested deeper than the budget lists through the deployments console, not the library.
- The linkage is recorded under one profile per project: the manifest's default deployment mode plus the host's active lifecycle tier. A project that also publishes to another profile from the deployments console keeps that entry under its own key, and reads prefer the host's profile before falling back to a single or same-mode entry.
- Creation carries the manifest identity (name, app type, description, key) plus the platform target. Category and media (icon, cover, screenshots) are not imported from the manifest's `media` URLs; the deployments console's app row still owns those uploads.
- The browser directory picker (`showDirectoryPicker`) only exposes the folder name, not the absolute path; the dialog keeps the path input editable so users can complete it.
- Category taxonomy is declarative data in the deployments package; swapping to a server-driven catalog (e.g. appstore) is a data-source change only.
- Template versions carry `platformTargets` as free-form strings server-side; the vocabulary is enforced client-side only (`templatePlatforms.ts`), so the deployments server could tighten it to an enum.
- Publishing from a project folder needs the Host packaging bridge (`sdkworkTemplateInstall.listFiles`/`readFiles`): a composition without the `sdkwork-template-install` plugin can still open the publish dialog, but the selected app cannot be packed and the publish action reports the host failure. The host bounds the archive walk at 20,000 files / 24 levels and each read batch at 64 paths / 32 MiB (64 MiB for one file); an app beyond those bounds is refused rather than published incomplete. `.env` and `*.local` overrides plus key material are always excluded; checked-in per-profile `.env.<mode>.<environment>` templates stay in the scaffold and the app's `.gitignore` still decides everything else.
- The app scan treats a parsable `agent.app.config.json` as the independent-root marker and honors `apps/README.md`'s `common` role as an exclusion. `apps/` children without that manifest (including a runnable root that simply never got one) are ignored with a count, not republished; the project root is considered only when `apps/` itself is absent.
- Dedupe is account-scoped and key-based: a template is reused when the caller owns one with the same template key, even when the listing's recorded source app differs from the currently matched platform app (a re-discovered or re-linked app root). Two selected roots claiming the same key block both rows instead of silently merging their versions; the operator edits one key.
- A new platform app record is registered from the manifest's console card when the app root is not yet linked. An ambiguous multi-platform root (Flutter or a shared mobile shell) falls back to its first concrete declared platform — `ANDROID_APP`, `IOS_APP`, and so on — so it stays publishable; only an app declaring neither a card nor a platform blocks that row until it is linked in the deployments console.
- The download panel lists at most five pages of 100 owned templates and the first 50 marketplace results per search; larger catalogs remain in the deployments console. Installing from the marketplace requires the marketplace read scope; install itself needs the same signed-in account as publishing.
- Both template dialogs require an IAM user session (the account chip and author identity come from it). A deployment configured only with a static application access token has no user subject to own a template, so each dialog stays on its sign-in gate; the deployments console remains the fallback.
- The installed scaffold receives the template identity in its manifest, but its `apps/README.md` row is only added when the project already carries the canonical directory table; a README without that table is reported and left untouched rather than restructured automatically.
- Existing directories are never overwritten in `apps/` mode: a taken app directory gets a `-2`, `-3`, … suffix. A custom target overwrites same-named files inside the directory the operator picked (the picker owns that choice), and a custom target is not added to `apps/README.md`.

### Dev Note

The dialogs are browser-only surfaces: they render the shared `@sdkwork` publishing components, consume the deploy-app catalog from the deployments package, and open through the session-header entry and the `deployPublish` service, so no host-side deployment state lives here.
