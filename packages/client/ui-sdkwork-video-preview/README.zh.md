# @deepseek-ai/dsh-client-ui-sdkwork-video-preview

[English](README.md) | 中文

## 概述

在右侧边栏的文档标签页中绘制视频。本包在文档注册表中认领视频容器后缀——此前没有任何东西认领它们，因此视频会被报告成「非文本文件」——读取容器结构以弄清文件究竟是什么，并贡献对应的 keyed 主体，以完整的播放控制条播放它。当平台拒绝某个文件时，数字化的媒体错误会被替换为容器、编码，以及读者所需的转换方式。

<a id="what-it-registers"></a>
## 注册了什么

- **渲染器元数据** —— `ctx.documentPreviews.register(...)`，id 为 `@deepseek-ai/dsh-client-ui-sdkwork-video-preview/video`，`loading: 'bytes-complete'`，认领三十一个后缀。不声明 `priority` 即落在 `extension` 档。
- **主体** —— 同一个 id 在 keyed `sidebar.right.tab.document` 席位上的组件，使用注册时声明的插件内按标签页分桶的播放状态 store。
- **没人要的后缀。** MP4、MOV、WebM、Matroska、Ogg、AVI、ASF/WMV、FLV、MPEG、传输流、3GPP、RealMedia、VOB、MXF 与 DV 全部被认领。浏览器无法解码的容器是被刻意认领的：不被认领时它们会回退到纯文本读取器并被报告成文本，而对一个 `.wmv` 来说这恰恰是最错误的解释。有三类后缀被刻意留出：`ts` 与 `mts` 在本仓库是 TypeScript 源码（传输流改用 `m2ts` 认领），`tsv` 是制表符分隔的数据，`oga`/`mka` 归音频预览所有。

<a id="how-it-renders"></a>
## 渲染方式

识别先行，因为 `<video>` 元素回答的并不是读者关心的问题。`video/containers.ts` 读取文件自身的结构：

| 容器 | 读取内容 |
| :-- | :-- |
| ISO 基础媒体（MP4、MOV、M4V、3GPP） | box 树、影片头的时间刻度与时长、每条轨道的 handler 与样本描述编码、轨道尺寸 |
| Matroska 与 WebM | EBML 树：Segment 的时间码刻度与时长、每条 TrackEntry 的类型、编码 id 与画面尺寸 |
| MPEG 传输流 | 先读 PAT，再读 PMT 的 stream type，因此轨道类型不是按名称猜的。两种帧格式都会读取：裸 188 字节包，以及摄像机写出的 M2TS/BDAV 帧——后者每个包前面带四字节到达时间戳，同步字节因此落在距帧尾 188 字节处 |
| Ogg | 编码识别头，以及 Theora 的 24 位画面尺寸 |
| RIFF AVI | 每条流的 handler 与 handler 编码、视频流的 BITMAPINFOHEADER，以及主头的帧间隔与帧数——也就是画面尺寸与运行时长 |
| ASF | 流属性对象的媒体类型与 BITMAPINFOHEADER 的压缩编码，以及文件属性对象的播放时长减去其 preroll |
| Flash Video | 第一个视频 tag 的编码 id |

由此得到容器、轨道列表、时长与画面尺寸——足以判断是否值得交给平台，也足以在不能播放时解释该文件。**识别只是线索，不是判决**：平台支持的容器里仍可能装着它不支持的编码，因此通过识别的文件会真正加载一次来验证，元素的拒绝会与本预览已从字节读出的容器和编码一起报告。

**每一次读取都是全定义的。** 上述解析器一个都不允许抛出异常，因为主体刻意没有在识别外层包 `catch`——损坏的容器必须变成一句解释，而不是把面板一起带崩的异常。这一点靠两个结构性性质保证，而不是靠运气：所有字节都经由同一个守卫读取，越界即返回零（对 `Uint8Array` 取越界下标得到的是 `undefined`，而 `undefined` 进入长度字段会变成 `NaN`，从而悄悄让本该起作用的边界失效）；所有遍历都有上限——文件头扫描受字节预算约束，而合法文件会把元数据放在末尾的情况则使用可计数的元素预算。

每个字节身份对应一个 Blob URL，并随创建它的 effect 一并释放。

<a id="interaction"></a>
## 交互

控制条包含播放与暂停、已播与总时长、进度滑杆、静音与音量滑杆、按浏览器自身档位循环切换的播放速度，以及循环开关。第二行是缩小、放大、适应窗口与实际尺寸——与 office 系列预览同一套档位——外加画中画与全屏。

**「适应窗口」是舞台自己量出来的，不是一档缩放。**它由实测的舞台与画面尺寸算出，旁边的百分比就是真正施加到元素上的倍数——因此标签与画面不可能对不上。缩放上限只约束读者按按钮要来的倍数，不约束这个拟合值；这正是「适应窗口」对一个比舞台还小的片子依然名副其实的原因。

**画面尺寸来自容器，容器没有声明时才来自元素。**传输流把尺寸放在基本流里，而不是本预览所解析的表中，因此这类文件会在元素拿到元数据之后由元素量出。这不是锦上添花：完全没有尺寸时，缩放没有任何可以施加倍数的对象，控制条里的百分比在变，画面却始终停在样式表给它的那个大小。

只要查看器持有可聚焦元素即可使用键盘：`Space` 或 `K` 播放/暂停，`←`/`→` 快进快退，`↑`/`↓` 调整音量，`M` 静音，`L` 切换循环，`F` 切换全屏。

播放速度、音量、静音、循环、缩放比例与播放位置都保存在标签页 store 中，回到该标签页会同时恢复设置与位置。控制条下方是信息列表：容器、编码、画面尺寸、时长与轨道摘要。

**无法播放的文件会失去控件，但保留事实。**浏览器打不开的容器、或被元素拒绝的容器，没有可驱动的元素——因此控制条根本不渲染，而不是留在那里空转，舞台也不再是一个可聚焦的键盘播放区。留下来的是信息列表，它是面板中唯一不是操作入口的部分：对一个即将动手转换的读者来说，容器、编码、画面尺寸与长度正是他们需要的东西。这是与图片预览的有意差异——图片预览的失败态没有任何事实可给；视频身上没有什么能靠渲染得知，而这里每一项都是从它自己的字节里读出来的。

## 已知限制与后续工作

<a id="known-limitations-and-deferred-work"></a>
- **浏览器不解码的容器只解释，不播放。** AVI、ASF/WMV、FLV、MPEG-1/2、RealMedia 与 MPEG 基本流都会给出容器、从字节读出的编码，以及所需的转换方式。这是平台限制，不是本包的缺口：没有浏览器能播放它们。
- **被拒绝的容器能自述多少就报告多少，不能自述的则保持未知。** AVI 与 ASF 在各自的头里写明画面尺寸与运行时长，因此被拦下的 `.avi` 或 `.wmv` 依然会显示这两项——而这恰恰是这个状态最要紧的地方，因为文件已经无法通过播放来得知它们。FLV、MPEG-1/2、RealMedia、MXF 与 DV 在本预览所读取的表中都不声明这两项，传输流则把两者都放在基本流里：这些格子在能解码该文件的元素报告之前显示「未知」，无人能解码时则一直未知。
- **容器声明的运行时长四舍五入到秒，元素给出的则按播放头所在秒截断。** 容器自身的运行时长是帧数乘以它以整微秒存储的帧间隔——一秒的 AVI 声明的是 0.99999——因此会四舍五入；而进度条用来划分的是解码器的测量值，随播放头一起截断。
- **可播放容器内部的编码拒绝很常见。** 装着 MPEG-4 Visual 或 ProRes 的 MP4 会在询问元素之前就被判定为不可播放；装着 HEVC 或 AV1 的 MP4 会被尝试，但仍可能在未启用该编码的平台上被拒绝，此时解释会同时点名两者。
- **编码支持取决于平台，而非本包。** 同一个文件在一个浏览器能播、在另一个不能；预览只报告实际发生的事，不假装能抹平这种差异。
- **没有字幕、章节与多音轨选择。** 说明会报告文件带几条音轨，但无法选择轨道，内嵌字幕轨也不会渲染。
- **不做转码。** 不做任何重编码，因此不可播放的文件在读者转换之前始终不可播放。
- **字节上限由文档归属方决定，而非本包。** 预览会请求整个文件，因此可打开的上限由 `workspace-files` 的 `maxFileBytes` 决定（默认 32 MiB）。更大的视频在识别开始之前就会被拒绝。
- **识别只读取文件头部。** 签名、流 handler、节目映射表与 Matroska 元数据都位于文件头，扫描上限为 4 MiB。唯一例外是 ISO-BMFF 的 box 遍历：非 faststart 的 MP4 会把 `moov` 放在文件末尾——因此初始化信息只出现在后续分片中的分片式 MP4，以及 MXF 与 DV 文件，仅按后缀识别。
- **测试样本来自 ffmpeg。** 测试识别的是 ffmpeg 封装出的文件，容器与编码都是真实的，但样本库里没有相机、录屏软件或流媒体服务产出的文件。
- **画中画与全屏取决于平台。** 两者都提供了入口，在不实现它们的浏览器上会被拒绝；此时控件不产生任何效果，而不是报告一个平台本就无从报告的失败。

<a id="dev-note"></a>
### 开发备注

<details>
<summary>维护者上下文 —— 点击展开</summary>

`video/containers.ts` 负责识别，也是唯一命名容器与编码的地方；它不依赖 DOM，由 Node 环境的测试覆盖。`VideoPlayer.tsx` 负责元素、控制条与唯一的 Blob URL。`tests/make_samples.py` 用 ffmpeg 重新生成样本；改动解析器后请运行它，让测试始终识别真实封装器的输出。传输流样本是真正的 M2TS（192 字节帧），测试同时从它派生出裸 188 字节流，因此两种帧格式都被固定住。它命名为 `.m2ts` 而非 `.ts`，是因为 `.ts` 后缀在本仓库会与 TypeScript 冲突，linter 会尝试解析二进制。

测试直接钉住两条契约，因为二者一旦失守都会直接呈现在读者眼前：`VIDEO_EXTENSIONS` 里的每个后缀都必须是 `inspectVideo` 真能识别的（认领了却答不上来，文件就会落到一个只会说“这不是可读视频”的主体上）；任何字节序列都不能让识别抛出异常。第二条用刻意损坏的输入来检查，包括在元素中间被截断的文件、长度越过文件末尾的 box，以及指针字段指向缓冲区之外的节目表。

**端序是按格式分的，而且读错是无声的。**ISO-BMFF、Matroska、传输流与 FLV 的字段是大端；**RIFF 与 ASF 是小端**。RIFF 的 chunk 长度按大端读出来是几十亿，遍历于是把它夹到文件末尾，chunk 里的每个流头都被跨过去——于是一个 AVI 会报告「没有任何流」，编码为「未知」，而它的 `strh` 在第四字节就写着编码名。测试自己的样本构造器对齐的是**格式**而不是解析器：大端用 `u32`，小端用 `u32le`，而读取真实 ffmpeg AVI 的那条语料用例才是端序的固定点。

**两个小端容器都相对某个锚点陈述事实，而这两个锚点都对产商免疫。**RIFF 视频流的 `strf` chunk **本身就是** `BITMAPINFOHEADER`，因此它的宽高从 chunk 起点按固定偏移读取。ASF 的视频媒体类型把该头**内嵌**在一个 `VIDEOINFOHEADER` 里，而产商的填充方式各不相同——ffmpeg 就在它前面写了十一字节——所以宽高分别从 `biCompression` 四字符编码往前十二字节与八字节处读取，那是它们的填充挪不动的唯一偏移。有两个算术细节会实际影响准确性，测试把它们钉住而不是交给信任：top-down 位图的 `biHeight` 是**负数**，而 ASF 的播放时长**包含编码器声明的 preroll**，因此 ffmpeg 声明的 4.1 秒时长与 3.1 秒 preroll 描述的是一个一秒的片段。这个减法在头自身的 100 纳秒单位下、除法之前完成，因为 `4.1 - 3.1` 是 `0.9999999999999998`，会被向下取整成 `0:00`。

容器的标识符只会以**可打印 ASCII** 回显。Matroska 的 `CodecID` 是自由文本，因此它以文件写入的原样抵达面板；控制字符或双向覆盖字符会画出与文件所述不同的东西，而容器名旁边出现从右到左覆盖，是一次伪装，而不是一件趣事。

</details>
