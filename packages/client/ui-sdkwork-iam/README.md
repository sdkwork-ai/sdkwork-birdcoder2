# @deepseek-ai/dsh-client-ui-sdkwork-iam

English | [中文](README.zh.md)

## Summary


SDKWork IAM integration plugin: sign-in/register (full page + modal) and sign-out through the sdkwork-iam auth stack, mounted as the account app mode, the settings-menu account seam, and a frame overlay modal host.

## Surface

The plugin contributes these surfaces plus the `ctx.iam` service seam:

- **The account mode** (`mode.page` keyed `account`). The mode page mounts the sdkwork full-page auth surface (`SdkworkAuthPage`: password, phone-code, and email-code login, QR, plus email/phone registration and recovery, per the `ui-sdkwork-iam` settings toggles) while signed out; once authenticated it shows the account summary (display name, username, user id, email) with a sign-out button. Unconfigured, the page fails loud with the configuration notice. The mode is reached from the settings-menu sign-in gesture, not from the mode rail.
- **The modal sign-in host** (`shell.overlay` entry `iam-sign-in`): the settings-menu account seam's sign-in gesture opens the product login entry when the `presentation` setting is `modal` — the shared `LoginPanel` (brand mark and wordmark, welcome line, slogan, Sign in, Add API Key) that the desktop welcome window and the web account dialog render. The entry's Sign in runs the configured login gesture (`signInMethod`): the shipped `browser` opens the hosted authorization page in the system browser and shows a hand-off card that waits for the deep link, offers a retry, and — while it waits — copies the hosted authorize link so a browser that reported success without showing a window can still finish the login; `modal` raises `SdkworkSessionAuthLoginModal`, the account method form (password, phone code, email code, QR), without leaving the app. While the browser hand-off owns Sign in, the entry keeps that form as the quiet **In-app sign-in** link under the action column, so the pre-hand-off login mode stays one gesture away for a tenant that has not applied the registration; when Sign in already raises the form (configured `modal`, or no desktop bridge) the link is omitted and the entry does not repeat itself. A page without the desktop deep-link bridge always uses the in-app form. A caller whose own surface already showed the entry — the desktop welcome page, or its API-key page ending in `login` — runs the same configured gesture, so the entry never appears twice in a row. Add API Key opens the shell's sign-in page, whose key form writes the credential; a plain browser page owns no such page, and the entry omits that choice unless the deployment sets `brand.showApiKeyEntry: true` in the OEM profile. Without a configured base URL the modal opens into the configuration notice instead. A sign-in surface opens only from an explicit gesture — this menu row, or the sign-in button on a gated mode page's signed-out notice (`AuthenticatedModeShell`). No mode switch, submission, or page mount raises it: a gated page states its requirement in place. The host portals its dialog to the document body at the top of the surface stack (z-index 1200, above page modals, commerce dialogs, menus, and toasts) and restores the input and accessibility state a Radix dialog takes from its siblings — `pointer-events: none` on the body and `aria-hidden` on every other body child — so a caller that raises sign-in from inside its own modal shows an operable login card instead of hiding it behind that modal.
- **The desktop sign-in page**: `requestSignIn()` — the demand behind `ctx.iam`'s deferred requirement — opens the shell's welcome page over a running workspace when the `dshDesktop.auth.openSignIn` bridge exists, instead of going straight to the modal. `'login'` then runs the configured login gesture described above (the in-app form by default), `'credential'` means the user stored an API key instead, and `'dismissed'` answers "no"; the page never holds tokens, and the workspace document is not reloaded. The service takes the overlay store's bound actions when that host mounts and presents through them, so a request recorded before the first render — a launch hand-off or a failed cold-start callback — raises its hand-off or failure card at that mount. The login gesture itself does not wait for the mount: the hosted page is the login surface, so a request whose overlay has not rendered (or never renders) still starts the browser login instead of disappearing into an unbound surface. The in-app account form exists only inside the host, so that gesture keeps the request for the mount rather than consuming it with nothing to show. The gesture is read from the IAM settings namespace with a bounded wait (two seconds): the request runs at boot, before the Host settings document necessarily arrives, and the defaults could otherwise start the browser hand-off for a deployment configured for the in-app form. A plain browser page opens the in-app form directly.
- **The settings-menu account seam**: the plugin replaces the menu's anonymous account source through `ctx.account.setSource` — signed out it advertises the sign-in row (登录 / 注册) with no configuration required, signed in it publishes the display identity and enables the footer sign-out, which asks for confirmation before ending anything.
- **The sign-out confirmation host** (`shell.overlay` entry `iam-sign-out`): the question every sign-out gesture raises — the settings popover's footer row, the account mode's sign-out button, and the `个人主页` section (`ui-sdkwork-profile`). Confirming ends the session on the hosted auth origin the login opened: the desktop shell signs in as an OAuth public client, so it opens that client's OAuth logout (`<iamAuthorizeBaseUrl>/oauth/logout?client_id=<clientId>`) through the shell bridge, while a page-local session (the in-app account form of a plain browser page) opens the hosted sign-out page (`<iamAuthorizeBaseUrl>/oauth/sign-out`) in a new tab. Either way the system browser reaches a domain the user signed in on, and no product portal is involved. The dialog is a `shell.overlay` entry of its own (store `iam-sign-out`) because the sign-in store's steps must not inherit a session end, and it portals to the body for the same stacking reason as the sign-in host.
- **`ctx.iam`'s profile snapshot**: `profileSnapshot()` publishes the signed-in account as one memoized value (display name, e-mail, username, account id, organization/tenant ids, personal vs enterprise, environment, app id, management-center origin, sign-out URL on the login origin) for the `个人主页` section. The cache is keyed by controller state plus the environment facts, so the section's hook observes a stable reference until a fact moves.
- **`ctx.iam`**: the IAM service face — the sdkwork auth controller over the generated `@sdkwork/iam-app-sdk` client, the `ui-sdkwork-iam` settings mirror, the sign-in presentation dispatch (modal vs page), the account-profile reads and writes (`retrievePersona`, `updatePersona`), and the selectable catalog (`retrievePersonaCatalog`) that the persona picker consumes over the same client, base URL, and token manager.
- **The relay session credential mirror**: the plugin keeps the signed-in `authToken` in the Host credential plane under `BIRDCODER_AUTH_TOKEN` through `remote.credentials`, and unsets it on sign-out. BirdCoder's relay accepts that token as its API key, and the desktop shell's `<DSH_HOME>/iam` mirror does not exist in a browser launch; without this write a browser sign-in would leave every relay request without a credential. The reference is a session source, never the relay's own key — the Host `birdcoder-account` plugin copies it into `BIRDCODER_API_KEY` only while no user key holds that reference, so an API key entered on the Models page always wins. The mirror is scoped to the `remote`/`remote.credentials` services, so a page without them (the welcome window, a headless composition) keeps its login surface and simply skips the write.
- **The BirdCoder provider-card notice** (`settings.models.provider-card`, keyed `llm-pi-ai`): on an unconfigured BirdCoder card it states that the relay uses the signed-in Auth Token and offers the sign-in gesture, which opens the same login surface the settings menu does. It renders nothing while a session is held or once the credential join reports the key, it sits on the row rather than inside the editor, and every other pi-ai route is untouched. The card's own API-key field remains the override path, and it is the only path in a composition with no Models section (the slot is then never declared).
- **The Chat failure row's credential fixes** (`conversation.chat.turn-error.sign-in` and `conversation.chat.turn-error.model-settings`): the missing-credential sentence keeps its words and turns two phrases into links. **Sign in** raises the entry modal through `openSignInOverlay` and falls back to plain text once a session is held; **Settings → Models** asks `ctx.settingsMenu` to open the Models page on the BirdCoder provider card, revealing that row. The labels arrive from Chat's localized copy, so the sentence stays one localized sentence, and both entries answer `MISSING_CREDENTIAL` alone.

## Configuration

The IAM base URL and tenant application id come from the shared [ui-sdkwork-env](../ui-sdkwork-env/README.md) profile — the active environment's `apiBaseUrl` is the IAM app-api origin and `appId` is the tenant application id; an empty `apiBaseUrl` keeps session restore and the auth surfaces off (the menu's 登录 / 注册 row stays advertised and opens into the configuration notice). A custom `sdkwork.iamBaseUrl` in the OEM profile replaces that origin in every tier; the generated client still appends the same `/app/v3/api/auth/...` paths with the same parameters and the `X-Platform: pc` header, so only the domain changes.

The hosted auth origin — the one the browser login opens and every session-end URL sits on — is the OEM profile's `sdkwork.iamAuthorizeBaseUrl`, shipped as `https://platform.birdcoder.com` for production and the matching `platform-<tier>.birdcoder.com` elsewhere. One value therefore moves the login page and its OAuth session-end endpoints together; the CloudRouter portal origin in the environment profile only backs the management-center links. The session-end endpoints are the OAuth group's `/oauth/logout` (client-scoped, the desktop session) and `/oauth/sign-out` (the page-local sign-out page), both owned by [`oauth-session.ts`](src/client/oauth-session.ts).

The in-app sdkwork auth surface is the account method form behind the product login entry. It carries the account methods the IAM tenant serves — password, phone code, email code, and QR (the `qrLoginEnabled` setting, on by default) — and commits each successful login through the shared token store, which mirrors the dual-token session into `<DSH_HOME>/iam/session.json` through the `sdkworkDesktop.iamSession` bridge. A later launch restores that session, so an already signed-in user skips the login surface and the action that demanded it simply continues.

The hosted OAuth browser login is the shipped login gesture on desktop, and it requires the tenant application's OAuth relying-party registration: `runtimeConfig.oauth.relyingParty` with `clientId: birdcoder`, `redirectUris: ["birdcoder://auth/callback"]`, `confidential: false`, and the `openid profile email offline_access` scopes. `agent.app.config.json` declares exactly that, and the tenant applies it through the PC admin relying-party surface or the app manifest. A shell that exposes the loopback listener uses RFC 8252 instead: each login presents `http://127.0.0.1:<ephemeral-port>/auth/callback` as `redirect_uri`, which the IAM OAuth client must allow for the desktop public client (wildcard loopback port, exact `/auth/callback` path). Loopback stays off until the deployment enables it (`sdkwork.iamLoopbackRedirect: true` in the OEM profile, or `DSH_DESKTOP_IAM_LOOPBACK=1`), and falls back to the registered custom scheme when disabled or when the shell declines the listener. Only a top-level document navigation reaches that listener: a request carrying an `Origin` header or a non-navigation Fetch Metadata mode is refused before it is forwarded, the `Host` must be the bound loopback authority, and both responses carry `no-store` and `X-Content-Type-Options: nosniff`. Do not enable it before the tenant registers the loopback redirect: the hosted authorize page rejects an unregistered `redirect_uri` with `OAuth redirect_uri is not registered for this client` before any callback can reach the app. A tenant whose relying-party registration is missing, disabled, or not bound to a deploy application fails on that page before any login UI: the app receives `server_error` plus the page's generic description, because the server's problem document (400 `iam_oauth_client_invalid` / `iam_oauth_authorize_invalid`, or 500 `iam_oauth_authorization_create_failed`) stays in the browser page unless the page forwards it in `error_description` — so a deployment without the registration sets `signInMethod: modal` until it lands. The pending flow has a deadline, and a browser-side authorization or completion failure is reported back through the same deep link (`error` + `error_description` + `state`), so the hand-off card shows the failure and offers a retry instead of waiting until the deadline. Closing the hand-off card hides it without abandoning the attempt, because the user may still be finishing in the system browser: the deep link that follows commits the session and raises a sign-in notice instead of reopening the dialog, while a real failure (a refused page, a rejected code) raises the failure card again. A flow that merely expires while the card is closed stays silent — it is a timeout the user walked away from. The redeem carries a stable per-install device id, so a new login replaces only that device's previous session: the browser session that completed the authorization and the user's other devices remain signed in. The redeem is at-most-once: the generated transport's retries are disabled for that one call, and a second delivery of the same callback observes the first attempt, because a retried or replayed single-use code can only be rejected after the server consumed it. The pending flow's deadline is four and a half minutes, inside the server's five-minute authorization window, so a late hand-off reports an expired login instead of a failed exchange; the failure's own reason (the runtime's message and detail) is rendered under the localized step line and logged to the console. The bridge is the standard `sdkworkDesktop` preload shape (`deepLinks` / `shellOpen`). The pending PKCE flow is persisted in renderer storage (verifier + state only, cleared on redemption or expiry), so a browser login that finishes after the app exits still completes when the deep link relaunches it; a callback with no pending flow is ignored rather than reported as a failure. A waiting login also takes the shell's last accepted callback every two seconds: the window event has no backlog, so a callback delivered while the renderer has no listener (a reloading document, or the moment before the plugin bootstraps) is recovered from the shell's `deepLinks.getInitialUrl` take instead of stranding the attempt until its deadline.

A redeemed session commits the same way the in-app form does: the complete session (dual tokens, rotating `refreshToken`, `sessionId`, and the AppContext) reaches durable storage first, then the shared `TokenManager` every SDK client reads, then the account endpoint (`/iam/users/current`) completes the identity — display name, split name, initials, e-mail, username — before the auth controller takes the session and schedules the pre-expiry refresh. That profile read is bounded and best-effort: failing or timing out degrades the cached identity to what the exchange returned, never reports a successful login as a failure. A 401/403 is the exception — the gateway refused the credentials every SDK client would use, so the login is reported as `session-rejected`, the just-written session is discarded, and no SDK client keeps dead tokens. The hand-off card's failed state names the step by the runtime's error code (authorization not approved, exchange failed, flow expired, callback unverifiable, host unsupported), so a failed login no longer describes itself as "the browser could not open"; it also offers the in-app sign-in, so a tenant whose relying-party registration has not landed is one click from a working form. A cold start whose redemption failed presents that failure and its recovery actions as soon as the overlay mounts, instead of leaving the user in an anonymous workspace with no explanation. The failed card also keeps a details link under the reason line: it shows the server's own problem document (HTTP status, wire code, trace id, and body) above the runtime's code, message, and detail, and the expanded report copies as one labeled text block, so a support report can name the failing server call instead of quoting one generic sentence. When the hosted page fails before it can hand anything back, the app re-asks the same anonymous authorization-bootstrap endpoint once, so that report still arrives instead of a bare `server_error`; while the report is open the card widens to give the document its measure.

The store is the credential authority: a pre-expiry refresh replaces the shared `TokenManager`'s pair immediately, and a token-only session write keeps the cached identity and AppContext, so a rotation neither blanks the account row on the next launch nor leaves SDK clients on the access token that is about to expire. Sign-out is one gesture with two independent halves. The browser half ends the hosted session on the login origin (the desktop's OAuth logout, or the page-local sign-out page), while the product half is authoritative on its own: the local session is revoked through the refresh token against the IAM app-api logout operation — which still works after the access token expired — and the local copy plus the shared credentials are cleared. The browser half never gates the product half: a browser that refuses to open, or a deployment whose hosted endpoint is unavailable, still ends the session locally and on the server. Once the local clear finishes, the service reports the sign-out to the desktop shell (`dshDesktop.auth.signedOut`), which owns the decision to return to its signed-out landing; a browser page has no such shell. An in-flight login is only declared failed once that attempt stopped waiting: expired, forged, and repeated callbacks are ignored, the card keeps waiting, and the real callback still completes the login. A callback the window event never delivered is taken from the shell while the attempt waits, so a dropped event settles the login instead of surfacing as an expiry. The attempt's carriers are released when it settles: expiry or a rejected exchange closes the loopback listener and stops the take, while a stale link that leaves the flow waiting keeps both.

The `ui-sdkwork-iam` settings namespace (host-side registration in this package's node half, exposed to the browser through the api-proxy's product namespace list) carries only the presentation and login toggles:

| Field | Default | Meaning |
|---|---|---|
| `presentation` | `modal` | How the settings-menu sign-in opens: the modal or the full-page account mode |
| `signInMethod` | `browser` | What the login panel's Sign in button starts: the hosted page in the system browser, or the in-app form (`modal`) for a tenant without the relying-party registration |
| `qrLoginEnabled` | `true` | Offer QR-code login on the auth surfaces |
| `oauthLoginEnabled` | `false` | Offer OAuth provider login on the auth surfaces |

The session is persisted in the desktop shell's OS-encrypted host copy (Electron `safeStorage` when available, owner-only atomic file under `<DSH_HOME>/iam/session.json`); a plain browser page has no OS secret store, so it uses `localStorage` under `dsh.iam.session`. On desktop the token payload is deliberately not mirrored into `localStorage`; a legacy local copy is migrated once and removed. The desktop copy carries the complete session (auth token, access token, rotating refresh token, session id, user, and AppContext); a commit whose durable write fails is rejected instead of claiming a login that would not survive the next launch. Verification-code login methods are hidden by default (the harness's app client does not speak the messaging verification-code API); registration and recovery proceed without a code while the backend policy permits, and the auth page honors the backend's fetched policy when it requires one.

## Implementation notes

- The runtime adapter (`iam-runtime.ts`) maps the `SdkworkIamRuntimeAuthRuntimeLike` surface onto the generated app client (dual-token auth mode) and keeps the client's credential state in step with the localStorage token store.
- The relay session mirror (`relay-credential.ts`) serializes its writes and writes each token once; a refused write is reported and retried on the next credential change. A signed-out mount clears a reference a previous page left behind, so a session that ended while the page was closed cannot keep authenticating relay requests.
- `@deepseek-ai/dsh-client-ui-sdkwork-iam/src/sdkwork-global-token-manager.ts` owns the browser-global `AuthTokenManager` shared by every SDKWork-backed client plugin. IAM login writes merged IAM and env credentials into that manager; Drive, Knowledge, Token Plan, Feedback, and Agents surfaces read the same transport instead of creating isolated managers.
- The auth surfaces are the sdkwork components; their Tailwind utilities come from `apps/web`'s Tailwind pipeline (`@source` into the sdkwork packages, `primary-*` aliased to the harness's deepseek brand ramp). Light form fields overlay `--dsw-alias-bg-overlay` and `--dsw-alias-border-l2` rather than the collapsed light `bg-layer-*` whites; dark fields use `bg-layer-1` against the elevated shell. The QR column uses the same shell fill; the frame around the white canvas is transparent. Overlay CSS ships as a CSS Module (`sdkwork-auth.module.css`) so the client bundle injects it.
- The package's tsc emit resolves `@sdkwork/*` to local declaration facades (`sdkwork-types/`) — the sdkwork source cannot be emitted portably into `lib/types`; the full typecheck against the real packages runs in `tsconfig.tests.json` (wired into `typecheck:contracts-ready`), which is the drift guard for the facades. The tsdown client bundle swaps in a path-free tsconfig so it inlines the private auth and i18n source packages, pins qrcode to its browser entry (its node renderers would drag `fs` into the browser bundle), and empties the one plain sdkwork stylesheet (an error-page css for a component this harness never mounts). The published package declares only the public `@sdkwork/iam-app-sdk@0.1.1` optional dependency; npm consumers never resolve the private source packages.

## Model Experience

The relay session mirror changes how a model request authenticates, never what it contains: it writes the signed-in token into the Host credential plane the BirdCoder route reads, and removes it on sign-out. It adds no prompt section, tool, or session content.

#### KV Cache effect

None; this package neither assembles nor sends provider requests.

## Known Limitations and Deferred Work

- **Verification-code login** — email/phone code login and verification-required registration need the messaging verification-code API; the harness app client does not expose it, so those methods are hidden or surface the backend policy's requirement.
- **QR and OAuth login** — off by default; enabling them needs the backend features and the QR/OAuth provider catalog.
- **Browser login needs the tenant's relying-party registration** — `signInMethod: browser` opens the tenant's hosted authorization page, which refuses to start the authorization until the tenant applies and anchors the `oauth.relyingParty` block from `agent.app.config.json` (`clientId: birdcoder`, `redirectUris: ["birdcoder://auth/callback"]`); the app learns only `server_error` unless the hosted page forwards the server's own report, so a tenant that has not applied the block sets `signInMethod: modal`.
- **Single personal session** — organization/login-context selection challenges surface the sdkwork dialogs, but the harness has no tenant administration; multi-tenant flows are untested.
- **The hosted session end is a deployment contract** — the URLs name the hosted OAuth group on the OEM profile's `iamAuthorizeBaseUrl` (`/oauth/logout` for the desktop client, `/oauth/sign-out` for a page-local session); a deployment whose hosted auth surface does not serve those endpoints opens a page that cannot end the browser session, while the product session is still revoked through the app-api and cleared locally.
- **A loopback login survives a renderer reload only while its listener lives** — the RFC 8252 listener (five-minute bound) lives in the shell, while the PKCE flow lives in the renderer; a reload rebuilds the page, which adopts the waiting redirect through `loopbackLogin.pending()` and takes a callback the shell accepted in the gap through `loopbackLogin.takeCallback()`, so the login completes within that bound. After it, the browser login has to be started again. The registered custom-scheme callback has no such bound: the shell keeps its last accepted URL for the waiting flow's take.
- **The shipped deep-link callback uses the short product scheme** — the brand registers `birdcoder://auth/callback`; RFC 8252 sections 7.1 and 8.4 ask for a reverse-domain private-use scheme, and the brand's application id (`com.sdkwork.birdcoder`) is that identity. An OEM profile may name `com.sdkwork.birdcoder://auth/callback` as `sdkwork.iamRedirectUri`; the Host accepts it, the packaged application declares it with the OS, and only the tenant's OAuth client registration has to follow. Section 8.10's distinct redirect per authorization server stays a deployment decision (every tier shares one callback), and a changed origin abandons the pending flow rather than redeeming a code against another authorization server. Both private-use forms RFC 8252 section 7.1 defines are accepted on the application-id scheme: `com.sdkwork.birdcoder://auth/callback` and the authority-less `com.sdkwork.birdcoder:/auth/callback`; the shipped short scheme keeps the authority-bearing form.
- **The loopback listener binds IPv4 only** — RFC 8252 section 7.3 recommends attempting both address families. The deployment registers `http://127.0.0.1:<port>/auth/callback`, so the listener presents that literal and does not fall back to `[::1]`.

## Runtime invariants

No runtime invariant companion is published; the account seam swap is a service call (`ctx.account.setSource`) whose contract the settings menu consumes unchanged, the IAM session facts flow through the sdkwork controller own state machine, and the auth surfaces mount through the standard keyed slots; session/presentation agreement is covered directly by this package client behavior specs.
