# @deepseek-ai/dsh-client-ui-sdkwork-markets

English | [中文](README.zh.md)

## Summary

Open Markets from the sidebar to browse SDKWork Plugins records, install a record's catalog target through the Host plugin manager, or manage locally installed plugins. The top-level tabs are Plugins, Experts, Skills, and Connectors in that order, and each tab has exactly one view: the plugin catalog, the expert catalog, the skill catalog, and the connector panel.

## Runtime requirements

The keyed page uses the generated SDKWork Plugins App SDK and Skills App SDK with the active gateway, locale, and shared IAM token manager. It renders remote catalogs only when the host has an application credential; otherwise it opens the application's sign-in surface. The Plugins catalog returns artifact descriptors, and this package converts Git and Drive sources into the standard plugin-manager spec before starting the Host install dialog. The Skills catalog reads marketplace records, categories, cloud installations, and package artifacts directly from the Skills API. The plugin also declares `slots`, `locale`, `layout`, `sessions`, `workspaces`, `env`, `iam`, and `theme`. Prompt-based plugin creation and skill actions use the sessions and workspaces services. The fork sidebar registry remains an optional service used to suppress the independently mounted SkillHub and MCP connector rows when their panels appear in this page.

## Browser bundle

The client plugin emits one `client.js` closure with self-contained CSS modules and inline SVG glyphs. The Experts catalog uses the generated Agents App SDK, the Connectors tab frames the SDKWork MCP connector plugin's own panel page, and the remote-expert create flow embeds the SDKWork Agents PC create surface, so the bundle inlines those sibling checkouts' sources (the joined `../sdkwork-*` workspace members; see the repository's `pnpm-workspace.yaml`), and local installs need those checkouts beside this repository. The Skills cloud catalog uses the generated Skills API client directly and does not embed the App Store Skills page.

## Runtime invariants

No runtime invariant companion is published; the mode state lives in the layout store's declared action set and the entry/page registrations follow the keyed dispatch; store/mode agreement is covered directly by this package's client behavior specs.

## Understand the implementation

The page keeps its Plugins navigation and local management views around the catalog owned by SDKWork Plugins. The catalog fetches plugin and category records through the generated App SDK, displays localized fields, and installs a record's catalog target through the existing Host installer. The Add action opens the source form for direct installation, while Create plugin continues to dispatch a prompt into a fresh conversation. None of Experts, Skills, or Connectors keeps a cloud-catalog/market sub-tab pair: each tab is one catalog or one panel. The Experts tab's My experts page uses the SDKWork Agents create flow for remote experts and guided prompts for local and personal-VM experts. Cloud-backed SDKWork views show the host's sign-in surface when no application credential is available.

The Skills cloud catalog is BirdCoder-owned and reads the Skills API directly. It presents featured records, recommendation cards, API categories, installation sorting, newest sorting, an installed filter, and a detail dialog. Its search field, installed filter and add affordance live in the page header: the catalog obeys that filter (the featured shelf included), publishes the installed count the header chip shows, and draws a featured shelf over a five-column recommendation grid. Search and category selection are server-side filters; every result page is loaded before client-side sorting. Adding a skill creates a cloud-library installation for the exact published artifact matching the record's version, and the UI blocks duplicate requests while that write is pending. It does not download the skill or register it in the local runtime; SkillHub owns local installation and execution. Transient add success and generic add failure use the application-wide Toast so the report survives leaving the Skills tab; missing-artifact and catalog-load failures stay beside the catalog.

The Plugins tab leads with the SDKWork Plugins catalog. The generated App SDK reads categories and plugin records from the SDKWork Plugins backend database. Featured cards and popular rows use the record's localized titles, descriptions, icons, usage counts, artifact source, and install target. Install hands the record's target to this package's Host adapter, which resolves Drive download URLs, validates archive checksums, and starts the existing plugin-manager installation dialog; the same adapter joins the Host bundle roster back onto each card so an installed record shows its installed version, offers an update when the catalog has a newer registry version, and can be uninstalled. A confirmed install, update or removal is then written to the backend with the catalog snapshot used at that moment, so each device keeps one durable installation record; a failed or cancelled Host result writes nothing, and a refused write is reported separately from the Host outcome. Manage opens the local installed roster, while Add opens the source installer. The catalog keeps its search, category filters, and action behavior, while this package positions its toolbar in the main category row and applies the compact page density. Catalog actions are disabled with a stated reason when the host lacks plugin-management capability, another install is running, or a record publishes no target. This package still replaces the upstream Plugins page, declares its seven plugin configuration slots, and provides the `pluginNavigation` service. SkillHub, the expert market, and the MCP connector keep their independent panels and suppress their duplicate sidebar rows.

## Model Experience

None, as the plugin adds no prompt content, tools, or session events; plugin creation and skill actions only submit user-authored text as an ordinary queued turn.

#### KV Cache effect

None; the flows add no provider-side cacheable content beyond the submitted prompt text.

## Known Limitations and Deferred Work

- **Empty panels** — the Experts view retains the App Store's own empty or construction face until the SDKWork catalog has content. The Skills cloud catalog has explicit loading, error, retry, and filtered-empty states. The Connectors tab no longer embeds the App Store's MCP page: its whole surface is the SDKWork MCP connector plugin's panel, whose market is served by the `sdkwork-mcp` application.
- **Empty experts roster** — the My-experts page renders count chips over an empty roster with the per-scope empty notice until the experts catalog store lands and feeds it; a just-created expert appears in the Agents editor but not yet in this roster.
- **Conversation-executed create flows** — create-plugin entries dispatch composed prompts because they author files; failures surface inside the conversation rather than in the page. Installing a plugin from a source runs the plugin manager's install pipeline and reports progress in the install dialog. The remote-expert create flow runs inside the page through the embedded Agents create surface.
- **Archive and Drive installs are Host-side** — the page passes the standard spec and never downloads a package itself; the profile's plugin manager owns the download, unpacking, limits, and cache under `.plugin-manager/sources`.
- **Gateway-gated remote experts** — the create flow's first step persists the agent through the Agents app API, so the remote row is disabled until the environment service carries a gateway; signed-out users hit the sign-in overlay at the transport gate.
- **Plugins page behavior** — the Marketplace owns its catalog search and category filters. This package places the catalog toolbar in the main category row and applies the compact page density. Its Manage action opens the installed plugin roster, and Add opens the source installer. Confirmed installs, updates and removals are synchronized to the backend per device only after the Host reports success; the database keeps the complete catalog snapshot the record had at that time, and a stored snapshot lets a plugin whose catalog row later disappears still be recorded as updated or removed. The independent SkillHub market keeps its own add-menu entry only while its panel is registered.
- **SDKWork catalog authentication** — the marketplace needs an application Access-Token to call the SDKWork Plugins App API. The Host renders the shared sign-in surface until an IAM session or static environment token is available.
- **The SkillHub market is a guest too** — the catalog, its install/disable/rollback flows, its persistence, and the SkillHub proxy belong to `@montersy123/dsh-skill-market`, linked in as the `plugins/dsh-skill-market` submodule and mounted by the web-app bundle patch. This page supplies the Skills chip, draws that plugin's registered panel inside it, declares the plugin's sidebar row embedded, and owns the copy a deployment with the row disabled shows; it does not reimplement the market. The panel is reached through the ledger — the plugin publishes no client service — so the two packages share exactly one string, its `skill-market` panel key, and the panel component must stay prop-free (it is drawn outside its declared seat). A market update ships through that package, and a rename of its panel key is what the bundle acceptance spec (`packages/bundle/web-app/tests/built-in-skill-market.spec.ts`) catches.
- **The MCP connector is first-party** — the connector catalog, the OAuth/API-key and `mcpServers` authorization, the managed `@deepseek-ai/dsh-mcp-client` entries, the scopes, the governance rules, the tool workbench, and the diagnostics belong to `@sdkwork/dsh-mcp-connector`, a first-party plugin of this repository (`plugins/sdkwork-mcp-connector`, shipping committed `lib/` and `ui/` artifacts) mounted by the web-app bundle patch. The connector market is no longer bundled with the plugin and no longer fetched from a public CDN registry: the plugin's Host half reads the catalog from the `sdkwork-mcp` application's database through that application's generated App SDK (`@sdkwork/mcp-app-sdk`), with the deployment credentials the `ui-sdkwork-env` settings section holds. This page embeds the whole panel page that plugin's Host half serves — the Connectors tab *is* that page, with no extra Cloud catalog chip — declares the plugin's sidebar row embedded, and answers the page's two host questions (the Workspace scope and the example-Prompt conversation); it reimplements none of the connector. The panel's own toolbar — its market / installed / tools views with their counts, the search field and the add action — is carried by this page's header row (the Skills tab's arrangement) and reaches the page as frame commands; the page's report of its view and counts comes back up to draw the chips. The tab therefore shows one row of chrome, and only the category rail stays inside the panel. The two packages share four strings — the `mcp-connector` panel key, the `/mcp-connector/ui/` page path, and the request/answer message names — and the bundle acceptance spec (`packages/bundle/web-app/tests/built-in-mcp-connector.spec.ts`) pins all of them against the shipped artifacts, together with "the catalog comes from the sdkwork-mcp SDK and no catalog is bundled". A connector update ships through this repository.
- **The Experts tab is one cloud catalog** — the SDKWork Agents expert catalog is the tab's only view: a featured shelf of curated collections, the 专家 / 专家团 switch, the 综合 / 最热 / 最新 sort capsule, the division chips and the card grid, all read from the Agents App API (`GET /app/v3/api/ai/expert_divisions`, `/experts`, `/expert_teams`, `/expert_collections`). One expert is one managed agent and a team is several of them, which is why the two kinds share one page and one filter rail. The tab no longer splits into an embedded App Store catalog and the built-in package's roster panel: `ExpertsCatalogPage` draws both kinds itself, and the built-in expert package (`@deepseek-ai/dsh-client-ui-sdkwork-experts`) keeps the behavior the catalog cannot own — the `@` picker, the six summon tools, the team engine and its settings page. The page suppresses that package's sidebar row because the tab is now the expert navigation entry, and the panel key (`agency-agents`) remains the one string the two packages share; `packages/bundle/web-app/tests/built-in-expert-market.spec.ts` pins it with the two composed rows. Card actions go through the package's `agencyAgents` Remote: "use" enables the expert or team first, then starts a conversation whose mention text is the package's own reference format. The page also keeps the catalog data-plane trigger that pushes the roster, teams and both persona locales into that Remote overlay, so the package's tools and picker serve the same catalog the tab shows.
- **Upstream's page is the fallback, never a companion** — a fork composition hides `ui-plugin-manager` while this row runs and brings it back when this row is switched off, so the plugin surface can never render twice; enabling both by hand is a load failure by design, not a duplicate page.

### Dev Note

<summary>Working context for maintainers — click to expand</summary>

The prompt dispatch serves plugin creation and guided skill actions. It calls `ctx.layout.setMode('code')`, starts a session through the workspaces runtime face, waits for that session to become current, and sends the composed prompt as a queued text turn.

The plugin-source form and SDKWork Marketplace share `@deepseek-ai/dsh-plugin-manager/source` validation. The generated Plugins App SDK supplies catalog records; the host adapter converts each Git or Drive artifact descriptor into an install spec and runs it through the same store and install dialog as manual source installs. Drive file records carry a SHA-256 checksum that the archive installer verifies.

The remote-expert create flow runs through `expertsHost.tsx`, the session/port adaptation template every SDKWork surface package owns: it binds the Agents, Memory, Voice, Skills, Knowledgebase, and Drive generated clients to the active gateway and IAM session (a request fired while signed out is held at the sign-in gate), re-derives them on environment changes, and reports gateway readiness to the create affordance. The capability package's create surface (basic-info dialog and editor) loads code-split on first use, and the knowledge-selection adapter is bound when that surface loads because its state lives in the capability package's own module registry.

The Connectors tab's frame protocol is the SDKWork MCP connector plugin's, not this package's: the page asks its parent for the Workspace scope (`mcp-connector:workspace-context-request`, answered on load and on request) and asks it to open an example Prompt in a conversation (`mcp-connector:start-session`, answered with `mcp-connector:start-session-result`). `mcpConnectorPanel.ts` owns those names and the panel key, `connectorBridge.ts` maps this application's Workspace/Session snapshots onto the scope — the current Session's Workspace, else the most recently used one, else the only listed one — and delegates the hand-off to `uiWorkspace.startSession(workspaceId, { prompt, whenDraftExists: 'replace' })`, read per hand-off so a row that activates later still counts; no Session is created here. `McpConnectorSurface.tsx` accepts both requests only from its own iframe on this application's origin. The connector's `main` registration is what makes the tab show the panel at all: the same `main`-ledger watch the skill market uses (`mainPanelWatch.ts`), which is why neither panel needs a client service from its package.

The framed page is a separate document, so it inherits neither this page's stylesheet nor its color scheme. Its own stylesheet is token-first — every surface, ink, accent, radius and elevation reads a `--dsw-*` alias with a standalone fallback, and it is flat: no card stroke, no card shadow, fill-only hover states — and `connectorTheme.ts` projects the **host's computed alias values** plus the resolved `color-scheme` into the panel document on each load and each theme change (`--accent` from `state-business-primary`, primary fills from `button-primary-fill` with `label-primary-foreground`, the tint from `state-business-tertiary`). An application theme switch, an OEM brand or a token change therefore repaints the panel, and the panel keeps no second palette. `--accent`, `--accent-hover` and `--accent-light` remain a soft contract with the shipped artifact, pinned by the bundle acceptance spec beside the panel key and the frame protocol.

The panel follows the application's resolved scheme rather than the operating system's: the injected `:root` declares `color-scheme`, and the iframe element carries the same value, so a dark application never flashes a light first frame.
