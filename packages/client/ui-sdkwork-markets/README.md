# @deepseek-ai/dsh-client-ui-sdkwork-markets

English | [中文](README.zh.md)

## Summary

The Markets app-mode plugin owns the `markets` sidebar quick entry and the keyed `mode.page` page. The page header carries the category tab bar (Plugins, Experts, Skills, Connectors) on the left and the catalog tools on the right: a per-category search field and, on the Plugins tab, the add affordance. The add trigger opens a two-item menu: "Create plugin" dispatches a skill-guided creation prompt into a fresh conversation, and "Add plugin market" opens the entry dialog, which records a market's provenance (GitHub `owner/repo`, Git URL, or local folder, with an optional Git ref and sparse-checkout path) and submits it as one composed prompt. Both flows run through the same prompt dispatch channel because the harness has no direct market API yet. The Experts tab's my-catalog affordance opens the full-page My-experts view: roster tabs (experts, teams) with their counts, a created/purchased source scope, and a create-expert trigger whose hover menu lists the three expert types. The remote type enters the SDKWork Agents create flow — the capability package's basic-info dialog (name, avatar, type, summary) first, then the agent editor (system prompt, model, memory, capabilities, preview chat) as a full-body swap — through the embedded create-expert host adapter; the local and personal-VM types keep dispatching their guided creation prompts into a fresh conversation. The remote row is disabled while no gateway is configured. The page is public: it renders signed out and mounts no IAM session face; the create flow's backend calls are held at the transport gate until the sign-in overlay resolves.

The Plugins tab is the product's plugin surface. Its sub-tab row leads with the **Plugin Market** — the community catalog provided by the `dshmarket` plugin, which the Web bundle pins in its dependencies and mounts in its own patch, so a shipped build has it without an installer step — rendered from the `market` control service that plugin publishes (`render({ surface: 'plugins' })`) — and that chip is the landing view, so opening Plugins and every re-entry lands on it; then the **cloud catalog** (the SDKWork App Store's plugin catalog), then this deployment's own `official` and `installed` views: the official/installed bundles, each bundle's own `plugins.bundle.config` form, the components it declares with their per-row switches, the install dialog, and a bundle's post-enable `plugins.bundle.activation` guidance. The market owns its own search, categories, install dialog, updates, backups, and diagnostics, so this page draws no chrome around it and duplicates none of it: while that chip is active the page keeps its **Add menu** (create plugin / add plugin market) in the header but drops its own search field, because a second search beside the market's own would read as broken. The market service is optional by construction: a deployment whose patch switches that row off, or that composes no Web bundle at all, keeps the leading chip and shows an install affordance that runs the same installation pipeline the local views use, while a deployment that holds the bundle but has not loaded its browser half yet shows the page-reload prompt that loads it, and a bundle that was switched off is sent back to the installed roster instead of being told to reload. The install affordance never offers a write on a deployment that does not manage a profile. This package **replaces** the upstream Plugins page rather than sitting beside it: it declares the seven plugin-configuration seats that page declared — a slot has exactly one declarer, so a second children table for the same key would make the client refuse to load — and it provides the `pluginNavigation` service that page provided, so a plugin contributing to either surface keeps working unchanged. The composition hides `ui-plugin-manager` for exactly as long as this row runs and restores it when this row is switched off, so the enabled plugin surface is always exactly one page. The Skills tab is a sub-root for the same reason: its leading chip is the **SkillHub skill market** — the independent `@montersy123/dsh-skill-market` plugin's own `main` panel, which this page draws in place rather than reimplements — and the cloud skills catalog keeps the second chip. The market is the tab's content, not a destination: this page takes the registered panel and renders it inside the chip's surface, and because the tab now owns that market's navigation it declares the plugin's own sidebar row as embedded, so the market has exactly one entry. The panel is drawn only while it is registered — the row is off, or the plugin's client half has not loaded yet — and the chip's surface then says the market is unavailable rather than leaving the tab blank; the add menu's market row switches back to this chip instead of leaving the page. That plugin downloads a skill into the harness skill root and publishes it to the running `ctx.skills` registry, so an installed skill needs no second integration step: the Skills settings page lists it and the model can invoke it. Experts keeps the single-view experience. The Connectors tab is the **MCP connector**, the independent `dsh-mcp-connector` plugin's own surface: its Host half serves the whole connector interface as a same-origin page at `/mcp-connector/ui/`, and this tab frames that page in place, exactly as the plugin's own panel does. The connector market, the connections and their OAuth/API-key authorization, the cross-connection tool workbench, the scopes and governance rules, and the connection diagnostics all belong to that package; this page supplies the frame and the two facts the page asks its host for — the Workspace scope a new connection defaults to, and the conversation an example Prompt opens — and it declares the plugin's sidebar row embedded, so the connector keeps one navigation entry. A deployment without that row gets the unavailable notice instead of a frame pointing at a route nobody serves.

## Runtime requirements

The plugin registers the sidebar entry and the keyed page through `ctx.slots`, the dictionaries through `ctx.locale`, and the mode switch through `ctx.layout`. The page is public — it renders signed out and mounts no IAM session face, so the catalog stays browsable before sign-in. The plugin declares `slots`, `locale`, `layout`, `sessions`, `workspaces`, `env`, `iam`, and `theme`. The add flows need the sessions and workspaces services: dispatch switches the frame to the `code` mode, runs the shared New Session flow, waits (bounded) for the fresh session to become current, and sends the composed prompt into it as a queued text turn. The Plugin Market's control is consumed as an optional service (`ctx.inject(['market'], …)`): it is provided by the `dshmarket` plugin that the Web bundle mounts at activation time, so the page waits for it instead of requiring it and attaches or detaches as that plugin loads or unloads. The fork sidebar's row registry is consumed the same way (`ctx.inject(['sdkworkSidebar'], …)`): when that column is mounted, this plugin declares the embedded skill-market and MCP-connector panels there, which keeps each plugin's own row out of the column; a bare web shell without the fork column simply has no panel list to filter. The connector panel's Prompt hand-off reads the Workspace surface's New Session capability as an optional service (`ctx.get('uiWorkspace')`): a composition without it reports the hand-off as unavailable inside the panel instead of silently doing nothing, and the Workspace scope itself comes from the snapshots this plugin already injects.

## Browser bundle

The client plugin emits one `client.js` closure with self-contained CSS modules and inline SVG glyphs. The market pages embed the SDKWork App Store PC surface, and the remote-expert create flow embeds the SDKWork Agents PC create surface, so the bundle inlines those sibling checkouts' sources (the joined `../sdkwork-*` workspace members; see the repository's `pnpm-workspace.yaml`), and local installs need those checkouts beside this repository.

## Model Experience

The prompt dispatch channel only submits user-authored text as a queued text turn; the plugin adds no prompt content, tools, or session events of its own. The conversation agent performs the actual plugin creation (guided by the available plugin-creation skill) and market addition (fetching the repository, sparse checkout when needed, and reading its plugin manifest).

#### KV Cache effect

None; the flows add no provider-side cacheable content beyond the submitted prompt text.

## Known Limitations and Deferred Work

- **Empty panels** — the Experts and Skills cloud panels render a construction or empty notice until their real catalog surface lands. The Connectors tab is not one of them: it frames the MCP connector plugin's own page.
- **Empty experts roster** — the My-experts page renders count chips over an empty roster with the per-scope empty notice until the experts catalog store lands and feeds it; a just-created expert appears in the Agents editor but not yet in this roster.
- **Conversation-executed add flows** — create-plugin and add-market entries dispatch composed prompts because no direct host market API exists yet; failures surface inside the conversation rather than in the page. The remote-expert create flow is the exception: it runs entirely inside the page through the embedded Agents create surface.
- **Gateway-gated remote experts** — the create flow's first step persists the agent through the Agents app API, so the remote row is disabled until the environment service carries a gateway; signed-out users hit the sign-in overlay at the transport gate.
- **Plugins-only add trigger** — the add trigger mounts on the Plugins tab (both the Plugin Market and the cloud catalog); the Experts tab's my-catalog affordance opens the My-experts page, and the Connectors tab has none, because the connector panel carries its own installed view. While the Plugin Market chip is active the trigger stays in the header and only the page's search field is dropped, since the market's own page carries its own search. The Skills tab mounts its own add trigger on both chips; its market row switches back to the market chip and appears only while the skill-market panel is registered, so the menu never lists a destination that cannot be shown.
- **The Plugin Market is a guest** — the community catalog, its install/update/backup flows, and its diagnostics belong to `dshmarket`, which the Web bundle pins in its dependencies and mounts in its own patch so a shipped build opens on the catalog with no installer step. This page supplies the tab and the viewport, renders the control that plugin publishes, and offers installation and reload affordances; it does not reimplement or pin the market's behavior, so a market update ships by bumping that pin. The control contract — service `market`, contract version 1, a `render` method — is pinned against the shipped artifacts by `packages/bundle/web-app/tests/built-in-plugin-market.spec.ts`, and a market release that changes it falls back here to the install/reload faces until this page catches up. The tab's install affordance exists only where the Host manages a profile.
- **The SkillHub market is a guest too** — the catalog, its install/disable/rollback flows, its persistence, and the SkillHub proxy belong to `@montersy123/dsh-skill-market`, linked in as the `plugins/dsh-skill-market` submodule and mounted by the web-app bundle patch. This page supplies the Skills chip, draws that plugin's registered panel inside it, declares the plugin's sidebar row embedded, and owns the copy a deployment with the row disabled shows; it does not reimplement the market. The panel is reached through the ledger — the plugin publishes no client service — so the two packages share exactly one string, its `skill-market` panel key, and the panel component must stay prop-free (it is drawn outside its declared seat). A market update ships through that package, and a rename of its panel key is what the bundle acceptance spec (`packages/bundle/web-app/tests/built-in-skill-market.spec.ts`) catches.
- **The MCP connector is the third guest** — the connector catalog, the OAuth/API-key and `mcpServers` authorization, the managed `@deepseek-ai/dsh-mcp-client` entries, the scopes, the governance rules, the tool workbench, and the diagnostics belong to `dsh-mcp-connector`, linked in as the `plugins/dsh-mcp-connector` submodule and mounted by the web-app bundle patch. This page frames the panel page that plugin's Host half serves, declares the plugin's sidebar row embedded, and answers the page's two host questions (the Workspace scope and the example-Prompt conversation); it reimplements none of the connector. The two packages share four strings — the `mcp-connector` panel key, the `/mcp-connector/ui/` page path, and the request/answer message names — and the bundle acceptance spec (`packages/bundle/web-app/tests/built-in-mcp-connector.spec.ts`) pins all of them against the shipped artifacts. A connector update ships through that package.
- **Upstream's page is the fallback, never a companion** — a fork composition hides `ui-plugin-manager` while this row runs and brings it back when this row is switched off, so the plugin surface can never render twice; enabling both by hand is a load failure by design, not a duplicate page.

### Dev Note

<details>
<summary>Working context for maintainers — click to expand</summary>

The prompt dispatch is the single execution channel for both add flows: it calls `ctx.layout.setMode('code')`, then `ctx.workspaces.startSession()` through the runtime face of the workspaces provision, and waits up to a bounded timeout for `ctx.sessions.list` to land a new current session before sending the prompt. When no session lands (connect failure, no workspace), the frame stays on the conversation surface where the user can act directly. The add-market dialog composes its prompt by template substitution with locale-owned fallbacks for blank ref and sparse-path fields.

The remote-expert create flow runs through `expertsHost.tsx`, the session/port adaptation template every SDKWork surface package owns: it binds the Agents, Memory, Voice, Skills, Knowledgebase, and Drive generated clients to the active gateway and IAM session (a request fired while signed out is held at the sign-in gate), re-derives them on environment changes, and reports gateway readiness to the create affordance. The capability package's create surface (basic-info dialog and editor) loads code-split on first use, and the knowledge-selection adapter is bound when that surface loads because its state lives in the capability package's own module registry.

The Connectors tab's frame protocol is the connector plugin's, not this package's: the page asks its parent for the Workspace scope (`mcp-connector:workspace-context-request`, answered on load and on request) and asks it to open an example Prompt in a conversation (`mcp-connector:start-session`, answered with `mcp-connector:start-session-result`). `mcpConnectorPanel.ts` owns those names and the panel key, `connectorBridge.ts` maps this application's Workspace/Session snapshots onto the scope — the current Session's Workspace, else the most recently used one, else the only listed one — and delegates the hand-off to `uiWorkspace.startSession(workspaceId, { prompt, whenDraftExists: 'replace' })`, read per hand-off so a row that activates later still counts; no Session is created here. `McpConnectorSurface.tsx` accepts both requests only from its own iframe on this application's origin. The connector's `main` registration is what makes the tab show the panel at all: the same `main`-ledger watch the skill market uses (`mainPanelWatch.ts`), which is why neither panel needs a client service from its package.

</details>

## Runtime invariants

No runtime invariant companion is published; the mode state lives in the layout store's declared action set and the entry/page registrations follow the keyed dispatch; store/mode agreement is covered directly by this package's client behavior specs.
