# Agent Note: 深链登录的一次性授权码最多兑换一次

Status: implemented

[English](2026-11-07-deeplink-login-at-most-once-redeem.md) | 中文

## 问题

桌面浏览器登录交给应用一个一次性授权码，应用通过生成的 `oauth.desktopSessions.create` 资源兑换它。该调用的两个性质与它承载的授权码不匹配。

生成的传输层对每个请求在传输失败、超时、5xx 与 429 上最多重试三次。这些情况都可能已经让服务端消费了授权码：重试随后返回“OAuth authorization code is invalid or expired”，运行时报告 `exchange-failed`，用户被告知登录失败，尽管浏览器已经完成登录，而且服务端可能已存在一个客户端从未拿到的会话。本地代理或网关 502 就足以触发。

待处理的流程还比服务端窗口活得更久。客户端等待十分钟（`DEFAULT_DESKTOP_FLOW_TTL_MS`），而 IAM 授权状态在托管页创建它之后五分钟过期，兑换要求它尚未过期。登录慢一点，或晚一点点击回跳，得到的就是一张仍在等待的卡片和一个服务端只能拒绝的授权码——同一张 `exchange-failed` 卡片，而且没有任何东西说明真正原因：卡片只渲染一行本地化文案，运行时的原因从未离开失败对象。

重复投递也是同一形态。托管成功页既自动触发深链、也把它做成可点击链接，而桌面 bridge 既把实时回调转发给渲染进程、又把它保留为启动 URL，因此同一个授权码可能被出示两次——并发地，或交给在事件之后才加载的渲染进程。

## 决定

兑换环节改为至多一次。`createIamDesktopLogin` 把桌面运行时绑定到一个基于生成传输层构建的兑换客户端上，带上 `retry: { maxRetries: 0 }`；该客户端在整个登录生命周期内记住它提交过的那一个授权码：同一回调的第二次投递观察第一次请求的结果，而不是再次兑换。真正失败的兑换由卡片的重试恢复，它用新的授权码重新开始浏览器登录，因此缓存一个已落定的失败不会让用户失去任何可行动项。

待处理流程的截止时间改为四分半（`IAM_DESKTOP_LOGIN_WINDOW_MS`），由服务端五分钟授权窗口推导，并为打开浏览器与回跳在途留出余量。在此之后到达的回调被报告为登录已过期，而不是仍在等待的登录兑换失败。

失败原因会被显示并记录。服务把运行时的 `code`、`message`、`detail` 保留为一条失败记录，打印到控制台，交接卡片在本地化步骤行之后原样渲染原因——它是文本化线路数据，永不本地化。

bridge 仍把实时回调保留为启动 URL 的同时转给它，因为仍在加载的窗口不能丢失这次交接；至多一次的兑换让这次重放变得无害，而不是第二次兑换。

## 考虑过的替代方案

**保留生成的资源并接受它的重试。** 重试是每个操作的传输层默认值，对其他所有操作都是正确的。对一次性授权码来说，它只会在真正成功之后制造一次假失败，而产品无法区分这两种结果。

**在传输错误时故意重试兑换。** 授权码可能已被服务端消费，也可能没有；再次出示同一个授权码要么失败，要么更糟——与真正成功的那次尝试竞争。重新开始浏览器登录是应用唯一能保证的结果。

**沿用运行时的十分钟并只在授权码被拒时解释失败。** 这个等待让一个已死的尝试在授权码过期很久之后仍存活，用户会对一个从未有机会的登录看到“兑换失败”；现在截止时间与服务端一致。

**只显示本地化那一行。** 那就是已发布的卡片。它对步骤判断正确，对原因判断错误，而报告此缺陷的机器没有留下服务端说了什么。

**只投递实时回调、不把它保留为启动 URL。** 这能去掉重放路径，但仍在加载的窗口会彻底丢失交接，登录会一直挂到截止时间；至多一次的兑换让保留 URL 变得安全。

## 影响

丢失的兑换响应、代理后面的 502，以及重复的深链，都不再对服务端已接受的授权码报失败。晚到的回跳被报告为登录过期，卡片的重新打开与内置弹窗登录两条路径都能解决它。今后每次失败都在卡片与控制台带上原因，支持报告能指出出错的步骤，而不是只有“登录未完成”。

测试固定了每一条性质：兑换端口对一个授权码只发一次 POST 且带 `retry: { maxRetries: 0 }`，对新授权码再发一次；服务转发四分半窗口；卡片在步骤行之下渲染宿主给出的原因；同一授权码的第二次投递观察第一次尝试，而不是再次兑换。[包参考](../../../../packages/client/ui-sdkwork-iam/README.zh.md) 说明了兑换与窗口契约。
