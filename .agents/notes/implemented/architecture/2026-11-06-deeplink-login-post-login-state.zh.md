# Agent Note：兑换成功的深链登录提交与页面内登录相同的状态

Status: implemented

[English](2026-11-06-deeplink-login-post-login-state.md) | 中文

## 问题

桌面浏览器登录在 sdkwork 认证服务之外兑换授权码：`@sdkwork/iam-desktop-auth` 交回双 token 会话，由产品自己提交。过去这次提交只写入持久会话、交给控制器、发布 token，仅此而已。页面内登录还多做一步：提交 token 之后读取 `/iam/users/current`，把账号资料合并到登录载荷之上，再让会话进入控制器。于是走浏览器登录的用户拿到的是“兑换载荷恰好带了多少就是多少”的缓存身份：下一次启动后账号行里的名字可能缺失或过期；交接卡片也把所有失败都说成“无法打开浏览器登录页”，包括授权被拒、兑换被拒与流程超时。

## 决定

`IamService.commitDesktopSession` 负责兑换之后的完整序列，顺序固定：写入完整会话（双 token、可轮换的 refreshToken、sessionId、AppContext）；解析运行时；把 token 发布到共享 `TokenManager`；读取账号资料并与兑换身份合并；用合并后的身份替换持久记录；排定预过期刷新；把会话交给控制器；清除失败状态；关闭交接界面。

这个顺序有三个刻意之处。运行时在发布 token 之前解析，因为构建它会用控制器状态重新播种共享管理器，而首次登录时控制器还没有会话——先发布再解析就会把资料读取所需的凭据清掉。持久的 token 写入是闸门：写入被拒绝就拒绝整次提交并保持未登录，这正是存储模式文档承诺的行为。资料读取有 5 秒预算且尽力而为：它运行时登录已经成功，账号接口变慢或失败只让缓存身份退化为兑换载荷，而不是把登录判为失败；它自己那次写入失败也保留已经落盘的兑换身份。拒绝是唯一例外：401/403 说明网关不接受每个 SDK 客户端都会使用的那份凭据，因此提交会丢弃刚写入的会话、在卡片上报 `session-rejected`，并让应用保持未登录，而不是呈现“已登录但之后每次调用都失败”。

交接卡片同时指出失败环节。`SdkworkDesktopAuthError` 本就带有稳定错误码与原因，服务把它们记为“最后一次失败”，并在新一轮尝试开始或成功时清除；浮层对已知错误码渲染一行本地化说明，并在其下原样给出宿主自己的原因。

## 考虑过的替代方案

**只依赖兑换载荷。** 它带 id，有时带邮箱；头部渲染的显示名、拆分姓名与首字母就只能从该载荷推导——这正是跨启动会变旧的那份身份。

**登录报告完成之后再懒加载资料。** 提交变短，但每个界面都要处理脚下变化的身份，而且迟早还得有第二次持久写入。

**资料读取失败就判登录失败。** token 已经有效、授权码已被消费，为一次展示性读取逼用户再走一轮浏览器，代价不合理。

**保留单一通用失败文案。** 它对一种原因（浏览器打不开）是准确的，对其余原因——配置错误的租户上最常见的那几种——是错的。

## 影响

深链登录到达与页面内登录相同的登录后状态：控制器会话带 AppContext 与补全后的身份，共享 `TokenManager` 在第一次需要鉴权的读取之前就持有两个 token，账号行与账号页在两条路径上渲染同一个名字，预过期刷新由同一个辅助函数排定。Host 侧不变：两条路径都由同一处提交写入 `<DSH_HOME>/iam/session.json`，中转凭据镜像读取的就是这个文件。

回归套件用真实桌面桥、真实认证运行时与真实 token 存储覆盖整条链：兑换、带鉴权的资料读取、合并后的身份、控制器状态、SDK 请求头、账号行、被门控的后端调用被放行，以及授权被拒、兑换被拒、流程超时三种失败。旧版本写入的身份仍然可用，因为恢复路径在记录只带显示名时仍会派生拆分姓名与首字母。[包参考](../../../../packages/client/ui-sdkwork-iam/README.zh.md)陈述了该序列。
