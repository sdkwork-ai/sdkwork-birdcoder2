# Agent Note: The persona-bot plugin ships from its git submodule and the assistant owns the rail cell

Status: implemented

English | [中文](2026-11-08-deepseekbot-assistant-surface.zh.md)

## Problem

The fork's mode rail offers Home, the generation modes, the App Store, Knowledge Base, Courses, Drive, Assets, Search and Token Plan. None of them reaches the persona-bot layer (DeepSeekBot, renamed Tobs by its upstream): the third-party plugin that gives agents persistent identity, memory and messaging. The repository the product asked this fork to integrate — the `sdkwork-ai/sdkwork-deepseekbot` mirror of `BotHarness/DeepSeekBot` — is the plugin's upstream for this fork and commits neither the host half's `dist/` nor the browser half's `lib/`. The first integration used the published npm closure for those artifacts, but the assistant naming (助理 / Assistant), the right-hand Dock tabs and the Assistant settings rename reached the mirror's `main` before any release carried them, and the product asked for the plugin to come from git rather than from a registry version.

The plugin also publishes no panel-rendering service. Its browser half registers its whole interface as one keyed `main` panel (`botharness`) plus a `sidebar.panellist` row, and swaps the left column for its own Bot-mode sidebar through a `sidebar` shadow while that panel is selected. A host that wanted the surface anywhere else would have to copy its component tree or re-register its slots, which the third-party read-only rule forbids.

## Decision

**The plugin is a git submodule this repository builds.** `plugins/sdkwork-deepseekbot` pins `sdkwork-ai/sdkwork-deepseekbot`'s `main`. Its three runtime packages are workspace members, so `packages/bundle/web-app` depends on them with `workspace:*` and the Web bundle, the Desktop runtime and the Desktop development project all resolve the build from this checkout. `scripts/build-deepseekbot.mjs` runs the submodule's own `tsdown` toolchain (installed by this repository's `pnpm install` because the submodule root is a workspace member): once after `pnpm install`, and as a `build:artifacts` gate. It skips only while its content stamp (`.dsh-build/deepseekbot-build.json`) still matches both the hashed build inputs and every artifact it produced, so a warm install pays nothing and a checked-out or edited artifact is never mistaken for the current one. No registry release stands between a plugin commit and the product. `cordis.patch.yml` mounts `botharness-core` (Bot registry, memory repositories, `/api/botharness/*` routes, bot session driver, `agentPreset: deepseekbot`), `botharness-client` (the browser half) and `preset-deepseekbot` (the plugin's generated agent preset); the plugin's own `dsh.bundle.patch` stays out of the profile's bundle list, so those rows are the single mount.

**Release inputs carry the plugin's own tarballs.** The runtime packages are private and versionless (`0.0.0`), so the `dsh` release family cannot carry them, and the packed `@deepseek-ai/dsh-web-app` manifest names them at `0.0.0`. `scripts/release/pack-assistant-plugin.ts` packs them beside the dsh family, so the Desktop package-set closure selects them from the same input set and the packed-install verification resolves them from it too; `sdkwork-deepseekbot`'s tarball is re-packed with a manifest that names the two mounted packages instead of its `link:` sibling sources. Nothing is published to a registry, and the packed bundle is meaningful only beside those tarballs.

**The release boundary refuses a browser bundle the module table cannot satisfy.** `scripts/release/pack-assistant-plugin.ts` scans the built `@botharness/ui` bundle's bare `require()` specifiers and fails the pack unless each one is either a `PLATFORM_MODULES` seed or a `dsh.client.external` declaration the boot graph materializes; `scripts/client-build-environment.ts` also digests `plugins/*/packages/client/lib/client.js`, so the bytes packed are the bytes the build recorded. Without the check a stale bundle that externalized `@tanstack/react-query` shipped as a release: the browser dropped the entire plugin at import (`require("...") missed the module table`) and the assistant cell, which follows the plugin's `botharness` main panel, disappeared with it, while the development launch kept working.

**The assistant's identity is the fork's, not the plugin's product brand.** The `botharness-client` row sets `botIcon: bot`, so the Bot-mode sidebar logo and the uncustomized steward's avatar draw the robot mark the rail cell also uses. The plugin's sidebar header renders the localized assistant name (`tob.defaultName`: 助理 / Assistant) instead of the product wordmark, and the preset row is registered as 助理. The fork therefore owns the assistant's name and mark on the plugin's own surface as well as on its navigation; the plugin repository records the naming decision in its ADRs 0304 and 0305.

**The host owns the surface's control rail.** `ui-sdkwork-assistant` declares `data-bh-host-rail` on `<html>` for the lifetime of its mount. The linked workspace reads it: it does not create its 56px icon rail, closes one that a saved layout restored, and gives a channel column narrower than 200px the rail's space (260px). The surface therefore keeps exactly one control column — this shell's mode rail — and the channel list, not an icon strip, is its left edge; panel switching, 助理设置 and exit stay reachable through the dock's sub-panel toggle, DSH Settings and the host chrome. The plugin's ADR-0306 records the contract, and an unset attribute leaves the standalone app's rail untouched.

**The assistant rail cell belongs to a fork package.** `packages/client/ui-sdkwork-assistant` registers one keyed `mode.rail.entry` under the new `assistant` mode id, second in the rail order (directly below Home) and in the fixed, unhideable set. The cell carries the product copy 助理 / Assistant and a robot-head glyph — outline at rest, filled while the panel is selected, the same two-weight selection the rail's other cells use — and it opens the surface by selecting the plugin's panel through `ctx.layout.selectPanel('botharness')` — the same navigation the plugin's own sidebar row uses. The plugin's interface, sidebar shadow and settings section remain its own registrations.

**The left column's entry is the sidebar's own quick-entry seat.** The same package registers one `sidebar.actions` entry (id `sdkwork-assistant`, order 35, directly after the scheduled-tasks entry) rendering the same robot glyph at the seat's 16/18px sizes with the 助理 label, no artwork background and no badge — the geometry, hover treatment and copy placement of the scheduled-tasks entry beside it. The plugin's own `sidebar.panellist` row, drawn with its avatar artwork and "试试看" onboarding badge, is suppressed through `ctx.sdkworkSidebar.suppressPanel('botharness')`, so each column keeps exactly one entry to the surface. The suppression follows the sidebar service, so a profile without that column still gets the rail cell, and unloading this package restores the plugin's row.

**The cell follows the panel, not the rail.** `assistant` never becomes the frame's mode: the frame renders a selected main panel inside the code surface, so the mode stays `code` and the rail's mode cells would otherwise keep Home lit. The cell therefore paints its selection from `usePanelInfo` (the panel selection), and `ModeRail` passes `active: false` to every mode cell while a main panel is selected. The cell's registration is gated on the `botharness` main-panel entry: a profile that disables the plugin's rows gets no dead icon, and a plugin teardown removes the cell with its panel.

**A stored rail layout adopts the new mode beside Home.** `normalizeLayout` now places every mode missing from a stored order directly after the nearest preceding shipped mode the order already carries, instead of appending it. An existing user's rail therefore shows the assistant cell where the product ships it rather than at the end of the rail.

**The assistant's composer renders the shell's conversation picker.** The shell's model-selection plugin registers the composer picker as the root-scoped `model.select` Component Factory over the same `ModelSelect` the conversation seat renders. `ui-sdkwork-assistant`'s main-panel entry passes the renderer's `renderFactorySlot`, the IAM sign-in gate and a reader for the shell's session model catalog down as host capabilities, and the assistant composer builds a directory snapshot from that session catalog — the same catalog Home renders — plus the bot's route, then renders the factory: trigger, two-level menu, provider search, badges, effort rows and the sign-in gate included. The gate uses the IAM in-place entry, so a preview model's sign-in request raises the shell's overlay instead of handing the screen to the desktop welcome page; the assistant surface stays selected. Because the picker reads that catalog directly, the provider groups (BirdCoder first, then the account providers), model names, sign-in previews and provider failures are Home's by construction, signed in or not; the Bot catalog remains the model plan editor and validation source, and the local menu is the fallback for a standalone BotHarness composition where the shell plugin is absent. The full editor (presets and the assignment model) stays on the bot's profile entry and in the model command. The bot's route still inherits the shell's default model while it has no plan of its own, so one default configuration reaches both conversations; `dm-composer-context.test.ts` and `assistant-model-picker.test.ts` cover the hosted factory, the session catalog snapshot, the standalone fallback and the catalog mapping, and `model-credential-health.test.ts` covers the Bot catalog's sign-in preview.

## Alternatives considered

**A pinned npm closure.** The first integration installed `deepseekbot`, `@botharness/core` and `@botharness/ui` at their published versions. It cannot adopt the mirror's `main` — the naming, Dock-tab and settings work is unreleased — and it makes a registry publication the gate on product copy. Git is the plugin's source of truth here, so the workspace consumes the submodule instead.

**A read-only `plugins/` submodule like the others.** The repository's default third-party pattern assumes a submodule that ships committed `lib/` artifacts. `sdkwork-deepseekbot` gitignores them and is this fork's own upstream, so the plugin is built here rather than run as shipped.

**Committing the built artifacts into the submodule.** The client bundle alone is about 23 MB per build, the upstream `.gitignore` excludes it on purpose, and every plugin commit would add a binary revision. Building on install is smaller and cannot drift from the pinned sources.

**Keeping the mtime freshness check.** A checkout can leave a stale artifact newer than every source it no longer represents, and the release then ships that bundle as if it belonged to the pinned tree. Content addressing costs one hash pass per build and removes that class.

**A mode page that renders the plugin.** A `mode.page` for `assistant` could carry the whole center column with its own chrome. It cannot mount the plugin's interface: the plugin publishes no `render()`-style service (unlike `@xmanrui/dsh-im`, whose `dshImClient` the IM connector page follows), and re-registering its slots or copying its components would make this repository a fork of its interface.

**Reusing an existing mode id for the cell.** Registering the cell under an existing mode (Search, Assets, …) would avoid the `AppModeId` change. It hijacks an unrelated icon's selection and page, and the customize dialog would name the wrong surface.

**A `mode.rail.panel` shortcut above Settings.** That is where the IM connector lives and it is a supported seat. The product asked for the cell directly below Home, so it has to live in the mode group.

**Mounting the plugin's Browser and Computer rows too.** `@botharness/browser` and `@botharness/computer` are optional capability rows with native dependencies (`sharp`, a bundled browser runtime). They are not mounted; a deployment that wants them adds the rows and their dependencies in a later patch layer.

## Consequences

- The assistant surface is navigable from both columns by default in a shipped build: the rail cell below Home and the sidebar quick entry after 定时任务. The plugin's own "Bot 模式" row is suppressed rather than restyled, so the plugin's bundle stays untouched and its row returns if this package is removed.
- The plugin's release identity is a gitlink on the mirror's `main`, so `pnpm run update:deepseekbot` moves the pin, relinks the workspace, rebuilds the artifacts and runs the acceptance spec in one step; a checkout that never initialized the submodule still installs (the `postinstall` build skips with a message, and the explicit build gate fails).
- The submodule root joins the workspace for its build toolchain only; `puppeteer` (pulled by its documentation tooling) is denied in `allowBuilds`, and the plugin's runtime packages are the members the bundles depend on.
- The packed `@deepseek-ai/dsh-web-app` manifest names the plugin packages at `0.0.0`. That is only resolvable beside the tarballs `pack-assistant-plugin` writes into the same release input set, which is exactly what the Desktop package closure and the packed-install verification consume; a registry publication of this fork's dsh packages would need a published plugin version first.
- The agent preset is copied into the fork's patch, because a preset row composes plugins by name. A plugin release that changes that composition needs the patch row re-synced by hand; the acceptance spec only checks the preset row's package.
- The assistant cell is fixed: the customize dialog can reorder it and cannot hide it, so the product's headline assistant entry cannot disappear from the rail.
- A plugin bundle that requests an unseeded module fails release packing instead of booting to a silently dropped plugin. The assistant cell exists only while the plugin's `botharness` panel is registered, so that failure would otherwise reach the installed application as a missing assistant entry.
- While the assistant panel is open no mode cell is lit, because a main panel is not an app mode. That is the same presentation the sidebar-launched panels already had, now stated in one place in the rail.

## Testing

`packages/bundle/web-app/tests/built-in-assistant.spec.ts` asserts the four composed rows, the workspace dependency on the submodule's packages, both plugin manifests' browser declarations, the built host half, browser half and preset helper, that the real browser bundle requests only seeded or declared modules, and rejects each incomplete form. `scripts/release/assistant-client-externals.spec.ts` covers the external gate's parsing and refusal. `scripts/build-deepseekbot.mjs` is the only producer of those artifacts; it runs from `postinstall` and as a `build:artifacts` gate, and the release pack job calls `pnpm run release:pack:assistant` so the verification install carries the same tarballs. The plugin's own `packages/client/test/bot-mode-sidebar.test.ts` covers the assistant name in the sidebar header, and its `packages/client/test/channel-dock.test.tsx` covers both the hosted case (no rail panel, the channel list present) and the standalone rail. `packages/client/ui-sdkwork-assistant/tests` covers both entries' registration lifetime, their click navigation, the rail cell's panel-driven selection, the sidebar row's copy and artwork-free layout, the plugin-row suppression, the `data-bh-host-rail` declaration's lifetime, and both entries' copy. `packages/client/ui-sdkwork-app-modes/tests` covers the new rail order, the fixed set, the panel-aware selection and the neighbor-aware adoption of a stored layout. `packages/client/ui-model-selection/tests/model-select.client.spec.tsx` renders the registered `model.select` factory and its plugin spec pins the factory registration and removal, while the plugin's `packages/client/test/dm-composer-context.test.ts` and `assistant-model-picker.test.ts` cover the hosted factory and the catalog-to-snapshot mapping.
