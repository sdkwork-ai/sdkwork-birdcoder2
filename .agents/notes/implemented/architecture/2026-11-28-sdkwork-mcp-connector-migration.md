# Agent Note: the SDKWork MCP connector replaces the third-party connector

Status: implemented

English | [中文](2026-11-28-sdkwork-mcp-connector-migration.zh.md)

## Problem

The Connectors tab answered "which MCP server do I connect" twice, and neither answer was the product's. Its leading chip embedded the SDKWork App Store's MCP catalog page — a second application's storefront that rendered an empty `未找到匹配的 MCP 服务` state because this deployment seeds no App Store MCP rows. Its second chip embedded `dsh-mcp-connector`, a third-party plugin pinned as a `plugins/dsh-mcp-connector` git submodule. That plugin owned the real connector market, the connection records, the OAuth/API-key grants, the scopes, the governance rules, the tool workbench and the diagnostics — but it loaded its catalog from a bundled `catalog/catalog.json` plus a public jsDelivr registry, so the shelf a person saw was whatever a third-party CDN and a package release agreed on, not what this deployment's data said. The duplicated chip row also made the tab the only market category with a "cloud catalog or the real thing?" choice.

The connector data itself belonged in `sdkwork-mcp`, which already owns the MCP domain's tables, App API and generated SDKs — and had no catalog tables at all, only placeholder server identities.

## Decision

**One connector surface, one catalog owner.** The Connectors tab is a single view: the SDKWork MCP connector's panel page, framed in place. The `云端目录 / MCP 连接器` sub-tab row and the App Store MCP embed are gone from `ui-sdkwork-markets`, together with their locale keys, their sub-tab state and the tests that drove them. The tab also has one row of chrome, not two: the connector page's own toolbar — the market / installed / tools views with their counts, the search field, the add action and the refresh control — moves into the application's category header row, the same arrangement the Skills tab uses. `McpConnectorSurface` forwards the header's state and commands through the frame protocol (`host-toolbar`, `host-view`, `host-search`, `host-add`, `host-refresh`, `host-locale`) and takes the page's view/count report back (`host-state`) to draw the chips; in that mode the page hides its own `.toolbar` and keeps only the category rail, while a stand-alone opening of the page keeps its full toolbar.

**The plugin becomes first-party.** `dsh-mcp-connector` is forked into this repository as `plugins/sdkwork-mcp-connector` (`@sdkwork/dsh-mcp-connector`), a workspace member that ships committed `lib/` and `ui/` like the other in-tree plugins, and the git submodule, its `.gitmodules` entry, its gitlink and the `dsh-mcp-connector` dependency rows are removed. The fork keeps the connector's whole feature surface and visual design — the panel page, connections, authorization, scopes, governance, tool workbench, diagnostics — and changes four things: its identity, its catalog source, its version-status surface (the plugin ships with the application, so no npm/GitHub update polling), and the docs/links that pointed at the upstream package. The scope is `@sdkwork/*` rather than `@deepseek-ai/*` because this is an SDKWork product plugin mounted from `plugins/`, exactly like the other entries there; a `@deepseek-ai/*` name would also read as a default-product package to `verify-default-product-isolation`, whose package registry does not discover `plugins/*`.

**The catalog lives in `sdkwork-mcp`.** Three new tables — `ai_mcp_catalog_entry`, `ai_mcp_catalog_server`, `ai_mcp_catalog_prompt` — join the MCP module's contract (1.1.0 → 1.2.0, seven → ten active tables). The connector catalog's data was imported once, faithfully (seven entries, 22 servers incl. one stdio mount, 44 prompts), into `database/catalog/catalog.json` and generated into `database/seeds/common/003_mcp_connector_catalog.sql` plus zh-CN/en-US display seeds by `tools/mcp_catalog_seed.mjs` (`--check` in the seed gate). The two categories the catalog needed but the taxonomy lacked — `finance`, `other` — are seeded with the rest, and the catalog's categories map onto the existing taxonomy (`企业数据` → `enterprise`, `法律合规` → `legal`, `效率工具` → `productivity`).

**The plugin reads that database through the generated SDK.** Two read-only App API routes — `GET /app/v3/api/mcp/catalog/entries` (published entries, `q` + `category_code` filters, nested servers and prompts) and `GET /app/v3/api/mcp/catalog/entries/{entryKey}` — are exposed by the Rust route crate, materialized into the App OpenAPI document and carried into the regenerated TypeScript and Flutter SDKs. `lib/sdkwork-catalog.js` resolves the deployment environment (`ui-sdkwork-env` settings → SDKWork host environment variables → explicit `catalogApiBaseUrl`/`catalogAccessToken` overrides), calls `mcp.listCatalogEntries` through `@sdkwork/mcp-app-sdk/generated`, paginates, maps every record onto the existing connector-descriptor shape, and hands it to the audit/merge pipeline the bundled catalog used to feed. The plugin ships no `catalog/` directory and no CDN fallback; the last successful catalog is cached in the plugin's storage domain keyed by the gateway that produced it. The sharing feature's trust root follows the cloud catalog too.

**The panel paints the application's theme, flat.** The framed page is a separate document, so it used to keep its own indigo palette, 1px card strokes and shadows; the tab showed an application-themed chrome around a panel that looked like a different product, and an app in dark mode still rendered a light panel driven by `prefers-color-scheme`. The plugin's stylesheet is now token-first and flat — every surface, ink, accent, radius and elevation reads a `--dsw-*` alias with a `light-dark()` fallback, cards carry no stroke and no shadow, and hover states are fill-only — and `ui-sdkwork-markets`' `connectorTheme.ts` projects the host's computed alias values plus the resolved `color-scheme` into the frame on load and on every theme change. The panel therefore follows the running theme, an OEM brand and any token change without a second palette, and the iframe element carries the same `color-scheme` so a dark application does not flash a light first frame.

## Alternatives considered

- **Keep the submodule and only swap its `catalogUrl`.** That leaves the third-party dependency, its npm update path and its release pin in place; the requirement was to remove the plugin, not to re-point it. The upstream catalog would also stay authoritative over this deployment's data.
- **Serve the catalog from the plugin's own storage instead of `sdkwork-mcp`.** The connector data is MCP domain data; a second store would drift from the App API the PC/H5/Flutter surfaces read, which is the divergence this migration removes.
- **Rewrite the panel as React components in a new client package.** The connector UI carries a decade of interaction detail (OAuth flows, scopes, governance, diagnostics). A rewrite would deliver a different surface, not the same surface with a different data source; framing the existing page keeps every feature and the visual design.
- **Register the new plugin under `@deepseek-ai/dsh-sdkwork-mcp-connector`.** Consistent with the fork naming contract for `packages/*`, but the default-product isolation gate treats an unknown `@deepseek-ai/*` workspace package as a violation because `plugins/*` is outside its registry, and widening that registry to four third-party submodules would pull their whole dependency closures into the default-product check.
- **Keep the bundled catalog as an offline fallback.** It is precisely the second copy of the same records that made the shelf disagree with the deployment. A deployment with no reachable MCP service sees an explicit failure instead of a stale shelf.

## Consequences

- This note supersedes the composition and catalog decisions in [`2026-11-01-built-in-mcp-connector`](2026-11-01-built-in-mcp-connector.md) (the submodule, the `catalogUrl` pin and the bundled catalog); that note's rationale for framing the page rather than re-declaring the component still holds, and the two cross-link each other. It partially supersedes [`2026-11-06-markets-cloud-catalog-first`](../feature/2026-11-06-markets-cloud-catalog-first.md): the connector's `cloud | connector` sub-root no longer exists.
- The Connectors tab renders one face: the connector panel. `packages/client/ui-sdkwork-markets/tests/markets-page.client.spec.tsx` asserts the tab frames the panel directly, that no `[data-connectors-subtabs]` row exists, and that a deployment without the row shows the unavailable notice instead of framing a missing route.
- `packages/bundle/web-app/tests/built-in-mcp-connector.spec.ts` pins the new row and package, both shipped entry halves, the panel page, the route module, the frame protocol in both halves, the four injected Host services, the `@sdkwork/mcp-app-sdk` dependency and the cloud-catalog module's SDK/`ui-sdkwork-env`/reader contract — and it fails if a `catalog/` directory comes back.
- The market is only as available as the deployment's `sdkwork-mcp` service. With no gateway the catalog is empty; with an unreachable one the last cached catalog stays on screen and the refresh reports the failure.
- A deployment must ship both halves: the `sdkwork-mcp` version that serves the two catalog routes and the plugin version that reads them. A plugin-only rollout shows an empty market; a service-only rollout changes nothing for older clients.
- Not yet owned: **catalog administration**. The three catalog tables are seeded from `database/catalog/catalog.json` and read-only through the App API; the admin console still manages categories and servers, and the PC marketplace still lists `ai_mcp_server` rows rather than catalog entries. Editing the market therefore means changing the seed source and re-running `node tools/mcp_catalog_seed.mjs`, exactly like the expert catalog's generate/check workflow.
- The plugin's `lib/` and `ui/` are committed, so a change to the connector's implementation is a change to this repository, not a submodule bump. `plugins/README.md` documents the fork provenance, the cloud catalog resolution order and the verification commands.
- Release packing treats the plugin like the other workspace-linked plugin rows: its manifest stays a `workspace:*` dependency of `@deepseek-ai/dsh-web-app`, `release:pack:assistant` packs its tarball (the `FORK_PLUGINS` list now names it), and the packed manifest pins `@sdkwork/mcp-app-sdk` at the facade workspace version. That version must therefore be published first: the `./generated` subpath export and `mcp.listCatalogEntries` were added to the facade at `0.1.6`, while `0.1.5` on the registry is the pre-catalog build. The plugin ships no `bin`, no registry metadata and no committed test scaffolding from upstream.
