# Agent Note：轮换中的凭据与进行中的登录保持诚实

Status: implemented

[English](2026-11-06-rotating-credentials-and-inflight-logins.md) | 中文

## 问题

桌面浏览器登录的第一轮排查之后还剩下三个缺陷，它们都只在登录“成功之后”才出现。

过期前刷新把新 token 写进了 token 存储，随后存储的变更钩子又把**控制器**的会话重新发布出去——而定时刷新从不更新控制器状态，所以控制器手里仍是刷新前的那一对。结果会话在存储里持续续期，而每个 SDK 客户端仍在发送即将过期的 access token，一小时后所有调用开始 401，直到应用重启。

token 轮换只写 token。缓存身份与 AppContext 没有在这次写入中保留，于是刷新可能让下一次启动后的账号行为空，尽管持久会话仍能通过鉴权。

深链桥把“本次启动携带了回调”的标记保留了整个进程生命周期。启动用该标记进入工作区而不是欢迎页；在 macOS 上用户退出登录并关闭窗口之后，同一个标记会让外壳跳过本该显示的欢迎页。另外，控制器拒绝消费的回调——过期的链接、伪造的 state，或操作系统把同一个回调投递两次——也会走失败通道，把交接卡片翻成失败，而浏览器里的真实登录仍在进行。

## 决定

token 存储是共享传输层的凭据权威。它的每次读取、写入与清空都上报快照；服务保留最近一次观察到的会话并发布**它**，只有在尚未观察到任何会话时才回退到控制器状态。因此控制器的一次状态变更会把刷新后的那一对重新发布出去，而不是旧的。

会话写入在它替换的记录之上合并：没有声明 `user`、`context` 或 `sessionId` 的快照，从它所覆盖的持久副本继承这些字段。新登录仍会替换它自带的身份；轮换不会抹掉它无法重述的东西。

深链桥的启动回调标记在渲染进程取走 URL 时退役。启动在任何窗口存在之前捕获一次，并用这个捕获值决定首个窗口；之后的决策看到的是退役后的值，因此登录式启动不再在一次退出登录后压制欢迎页。

回调失败只有在这次尝试已不再等待时才算登录失败，而 `no-pending-flow` 与 `state-mismatch` 永远不算：控制器对陌生或过期链接故意保留流程，好让真实回调完成它；已消费回调的第二次投递也不是一次失败的登录。

## 考虑过的替代方案

**每次控制器 emit 都异步读存储再发布。** 正确，但把同步订阅变成每次状态变更都走 I/O 的路径；观察到的快照等价且更便宜。

**让刷新去更新控制器状态。** SDK 的定时刷新与所有宿主共享，且刻意不碰产品状态；让定时器写控制器，等于给一个只有凭据消费方读取的值引入第二个写入者。

**把启动标记保留整个进程生命周期。** 这是更早的契约，代价是在之后一次退出登录时悄悄用工作区替换了欢迎页。

**上报每一个被拒绝的回调。** 用户会在浏览器仍在登录时看到“登录失败”，而卡片提供的重试会替换掉仍然有效的 PKCE 流程。

## 影响

刷新后的那一对无需重启就到达每个 SDK 客户端，`<DSH_HOME>/iam/session.json` 镜像出的中转凭据跟随同一个值。轮换保留缓存身份与 AppContext，因此账号行能跨启动存活。过期、伪造或重复的回调不再打扰进行中的尝试与卡片，登录式启动在退出登录后也会重新显示欢迎页。

回归套件把这些都钉住了：由短寿命 JWT 驱动的真实定时刷新必须替换共享凭据，并且在之后一次控制器 emit 后依然保留；token 存储必须在只写 token 的写入中保留身份与 context；深链桥必须在取走 URL 时让启动标记退役；重复回调与过期回调必须让 `browserSignInFailed()` 保持 false，同时尝试继续进行。[包参考](../../../../packages/client/ui-sdkwork-iam/README.zh.md)陈述了凭据与失败行为。
