# Agent Note: 技能 tab 直接绘制 SkillHub 技能市场

Status: implemented

[English](2026-11-01-skills-tab-embeds-skill-market.md) | 中文

## Problem

市场页的技能 tab 过去把 SkillHub 社区市场做成一次移交：一张说明市场是什么的卡片，加一个把技能市场插件的 `main` 面板选中的按钮，由它把中栏整体换成市场自己的页面。那个安排来自当时的判断——市场是一个只读的第三方包，只注册整页面板、不发布任何客户端控制（见[内置的 SkillHub 技能市场](2026-11-01-built-in-skill-market-plugin.zh.md)）。

这带来两个产品代价。市场成了一个需要跳转过去的第二页面，于是这个本该用来找技能的 tab 自己什么都不包含。而插件自己的侧边栏行仍留在列内、紧挨着 tab，同一个目录有了两个导航入口——其中一个还落在需求大厅一组快捷入口之下，没有人会去那里找技能。插件仍然同时注册面板和行，而这一行只能由持有该面板导航的表面移除。

## Decision

技能 tab 自己绘制已经注册的面板，并抑制插件自己的侧边栏行。

### 面板经由 ledger 跨包传递

`packages/client/ui-sdkwork-markets/src/client/skillMarketPanel.ts` 本来就在监视 `main` ledger 中 `skill-market` 这个 key，用来判断跳转是否可用。它找到的那条注册本身就带着插件的组件，因此同一个源现在发布 `{ component }`，并且只在面板变化时换引用：每次读取都返回新对象会让市场在任何无关面板注册后被重新挂载。

`SkillMarketSurface.tsx` 把这个组件画进 `[data-skill-market-embedded]`——一个具有确定高度的 flex 盒子，因为面板按 `height: 100%` 撑满并自行滚动它的卡片网格——没有面板注册时（该行关闭，或插件浏览器半边尚未加载）则画不可用提示。把它画在其声明的 seat 之外之所以安全，只因为市场面板不接收任何 slot props：它把状态放在本地，并通过同源的 `/skill-market/api/*` 前缀与其 Host 半边通信。这两点都是关于已发布产物的既成事实，而不是本仓库能够控制的契约。

市场的任何部分都没有被复制：没有目录、没有详情抽屉、没有安装流水线。submodule 保持未修改。

### 只有一个导航入口

fork 侧边栏的注册表 `ctx.sdkworkSidebar` 新增 `suppressPanel(panelId)`。列内的 `sidebar.panellist` 行是该列拥有的投影，因此把某个面板内嵌到自己表面里的插件在此声明该面板的行已内嵌，投影就会略过这一行。这个声明是一个由 Cordis 拥有的 effect：卸载市场插件即恢复该行。

市场插件以可选方式消费该服务（`ctx.inject(['sdkworkSidebar'], …)`），与插件市场的 `market` 控制一致：没有 fork 列的组成本来就没有面板列表可过滤，也不能因此激活失败。

这条行列表规则与列内既有的另一条规则一致：模式栏已提供快捷入口的面板同样不再单独列出。区别只在于判定权从第二个槽位变成了一个显式声明。

### 其余入口

技能子 tab 条保留两个 chip，云端目录打头，市场在旁（顺序由[每个市场分类都落在云端目录](../feature/2026-11-06-markets-cloud-catalog-first.zh.md)决定）。技能添加菜单里的市场行不再离开本页：它切到市场 chip，并且只在面板已注册时存在。移交文案（`skills.market.open`、`skills.market.cloud`、三行能力说明与署名脚注）随卡片一起删除，只保留「该部署没有市场」时的提示。

市场仍然可以作为一个 `main` 面板被选中。已经没有任何产品表面会导航到它，而布局也不跨启动持久化面板选择，因此它不会以孤立页面的形式重新出现。

## Alternatives considered

**fork 或给 submodule 打补丁，让它发布渲染控制** —— 即 `dshmarket` 的形态（`ctx.market.render()`），让这个 tab 反过来调用市场。代价依旧不对：该包是只读 submodule，构建产物随源码提交，每次上游发布都会变成一次合并。读取注册本身已经拿到同一个组件，且不需要向该包索取任何东西。

**由 fork 自有的包装包重写市场表面** —— 在本仓库里复制目录、详情抽屉、安装流水线与持久化，然后手工跟随每次上游发布。仍然因为「市场不被 vendored」的同一个理由被否。

**重新声明 `main`，让页面能用 `renderSlot`** —— 设计上不可能：一个 slot 只能有一个声明者，而 `main` 属于布局；第二份 children 表就是加载失败。绘制已注册的组件是唯一不破坏布局所有权的路径。

**注册一个隐藏的 `mode.rail.panel` 条目来复用既有的行过滤** —— 列内已经会丢弃 id 出现在模式栏快捷入口席位里的面板，因此一个渲染 null 的组件可以在不碰侧边栏包的前提下得到同样的过滤行。但它断言了一个产品并不存在的模式栏快捷入口，而且将来一旦在该席位外面加了外层包装，就会冒出一个空控件。

**在侧边栏里硬编码 `skill-market`** —— 最省事的过滤，也是错误的所有者：这一列会带上下游某个产品表面的知识，下一个内嵌插件又要再改它一次。

## Consequences

技能 tab 现在就是市场：浏览、搜索、安装、已安装/本地导入管理与市场自己的收藏都发生在人找技能的地方，目录也只有一个入口。插件保留它的 `main` 注册，因此任何想要它的表面仍可选中该面板。

耦合是一个字符串加一个形状，两者都是软约束。面板 key 已经由 `packages/bundle/web-app/tests/built-in-skill-market.spec.ts` 钉住，改名会先让用例失败而不是让 tab 失败。「面板不读 slot props」没有任何自动检查：将来某个版本若开始读取某个 slot 席位，从本 tab 绘制时就会缺少它们。对固定产物的手工验证是这方面唯一的闸门，这里明确记录而不是隐藏；补救办法是把面板退回导航之后，而这正是上一版设计仍然描述得清楚的形态。

抑制是按组合生效，而不是按部署配置生效：若某个部署希望市场保留独立页面，它不能在本插件页面挂载期间依赖插件自己那一行。
