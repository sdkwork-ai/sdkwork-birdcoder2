# Agent Note: SDKWork dependency declarations follow the real import closure

Status: implemented

English | [中文](2026-08-23-sdkwork-on-demand-dependency-closure.zh.md)

## Problem

`tsconfig.base.json` declared 361 `@sdkwork/*` path entries although the repository imports a fraction of them: 73 entries pointed into `sdkwork-cloudrouter` alone (mostly `sdkwork-cloudrouter-pc-admin-*` app-shell packages), plus blocks for account, models, payment, partner, messaging, rtc, log, documents, and catalog — none of which are workspace members or imports of this repo. The import-coverage gate (`scripts/sdkwork-dependencies.ts`) scanned the `src` trees of every pinned manifest repository, so any app shell's imports (cloudrouter's `src/admin`, `src/console-business`, `src/token-plan`) demanded a mapping, and `packages/client/tsdown.client.ts` turns every non-wildcard entry into a client-bundle alias. The manifest itself pinned 32 repos while only 24 have workspace members, lockfile references, and Dockerfile copies. The desktop app and token-plan therefore looked dependent on cloudrouter admin for no reason.

## Decision

- **Path declarations equal the transitive import closure.** The `@sdkwork/*` section of `tsconfig.base.json` now contains exactly the keys covering specifiers imported by local sources, the sibling workspace members joined in `pnpm-workspace.yaml`, and — iterated to a fixpoint — the packages those mappings resolve into. 361 entries became 79. The section is generated by `node scripts/analyze-sdkwork-closure.mjs --rewrite` (new script), which also derives missing mappings for joined members and heals stale targets by package name.
- **The gate checks both directions.** `checkSdkworkImportCoverage` now scans the closure instead of every pinned repo, so an unjoined app shell's imports cannot drag mappings in. A new `checkSdkworkPathDeclarations` rejects a declared key no closure import covers and rejects duplicate keys. The `sdkwork-dependencies` gate therefore fails on drift in either direction.
- **The manifest pins only repos the workspace joins.** `scripts/sdkwork-sources.manifest.json` drops the eight repos with no workspace member, lockfile reference, or Dockerfile copy (account, audio, cloudrouter, image, models, music, search, video); release builds and CI checkouts no longer fetch or pin them.
- **Stale member declarations removed.** `pnpm-workspace.yaml` dropped two members pointing at nonexistent `apps/*/packages/sdkwork-*-backend-sdk` directories; the real packages live under `sdks/`, and the tsconfig targets healed to those paths.
- **token-plan stays an independent brick.** `packages/client/ui-sdkwork-token-plan` imports nothing from cloudrouter; its seven `@sdkwork/*` imports (ui-pc-react, sdk-common, membership-service, membership-pc-subscription, order-service, order-pc-checkout, order-pc-recharge) are declared as `optionalDependencies` exactly matching the imports, and the page mounts on mode activation — the same high-cohesion, low-coupling brick style cloudrouter composes with.

## Consequences

- Client bundle alias tables shrink with the tsconfig section (they are derived from it), so a release build no longer carries cloudrouter admin resolution surface. CI clones and the release runner fetch 24 siblings instead of 32.
- Adding an SDKWork package now means: join it as a workspace member, add it to the manifest if its repo is new, re-run `node scripts/analyze-sdkwork-closure.mjs --rewrite`, and let the gate verify. Dead or duplicate declarations fail `verify-sdkwork-dependencies`.
- The two stale workspace members no longer hide broken paths; the generator heals moved packages by name so a mapping cannot silently point at a missing directory.

## Alternatives considered

**Keep scanning every pinned repo and add mappings for whatever its app shells import.** This is the status quo that dragged cloudrouter's admin/console/token-plan surface in; the closure scan is the same guarantee (everything the bundles compile is mapped) without unrelated app shells.

**Derive the closure from package.json dependency graphs only.** That misses `src`-level imports the client bundles compile through the path table (subpath and root specifiers both), so the gate would approve builds that fail on the release runner.

## Testing

- `pnpm run verify-sdkwork-dependencies` passes; `scripts/sdkwork-dependencies.spec.ts` gained four cases: unmapped import from a member, unmapped import from a local source, dead declaration, duplicate keys.
- `pnpm run typecheck` passes after the tsconfig rewrite (the pruned paths resolve every import the closure scans).
