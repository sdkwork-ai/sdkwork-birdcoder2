# Agent Note: The project row menu initializes SDKWork application access tokens

Status: implemented

English | [中文](2026-11-20-sdkwork-access-token-initializer.zh.md)

## Problem

Every manifest-bearing SDKWork application root carries one public application access token per profile — `.env.<profile>` for Vite roots, `env/sdkwork.<profile>.json` for Flutter, `config/mini-program/runtime-env.<profile>.json` for the WeChat mini program, and `config/app/runtime-env.<profile>.json` for Harmony native and other JSON runtime roots (`APP_ACCESS_TOKEN_SPEC.md` §2). The canonical writer is the repository-level `tools/materialize-client-env.mjs`, which also materializes URLs and bindings. There was no way to initialize the token matrix from the workspace browser for one project: the operator had to run a repository tool with the right environment variables, knowing which profile file each application format uses, and the tenant-level / organization-level claim difference (`organization_id=0` versus a non-zero organization, §3.2) was easy to get wrong by hand.

The fork already owns the project row's context menu. It did not own any action that reads or writes an application root through the browser's directory bridge, nor any action that signs a user in and issues a credential bound to that user's own applications. The public isolation token is forgeable by design, so a developer who needs an authorizing credential (and a product that must not let one user mint another user's credential) needs the authenticated exchange of `APP_ACCESS_TOKEN_SPEC.md` §8, not a second offline generator.

## Decision

A new fork plugin package `ui-sdkwork-access-token` (`@deepseek-ai/dsh-client-ui-sdkwork-access-token`) provides the access-token initializer, and the project row menu gains one row for `sdkwork-*` project directories:

- **The row** — `ui-sdkwork-workspace-row-menus` reads an optional `accessTokenInitializer` service from its inject face (`ctx.get`, so a composition without the new plugin keeps every other row) and shows **初始化 Access Token** only when the clicked directory's base name starts with `sdkwork-`. The same verb is also contributed to the shared workspace context menu through `ctx.contextMenus.register`, which is the right-click surface of a composition without the row-menus plugin.
- **The token** — `src/client/accessToken.ts` rebuilds `tools/app-access-token.mjs` §3 in the browser: fixed header (`alg: none`, `kid: public-app-token`), the required claims, tenant-level (`organization_id=0`, `TENANT`) or organization-level (non-zero organization, `ORGANIZATION`) derivation, the deterministic generation instants, and a decoder that fails closed on contradictory claims. A golden fixture pins the bytes to the canonical generator's output for both levels.
- **The discovery** — the dialog scans the clicked project directory (itself when it carries `agent.app.config.json`, else its `apps/*` children) and reads each root's identity from the manifest. A project without any manifest-bearing root gets an explanation, not a synthesized identity.
- **The write** — every selected root × profile is merged into that format's committed file: a dotenv file keeps every other line, a JSON runtime document keeps its other members, and a Harmony template keeps its nested shape. The whole request is validated before the first write; a single unreadable file fails only itself. Re-running an unchanged initialization reports every file as unchanged and writes nothing.
- **The file access** — the browser half never touches the filesystem: reads and writes cross the governed `uiWorkspace` directory bridge (`readTextFile`/`writeTextFile`/`listDirectory`/`createDirectory`), so the Host keeps its text bound and path rules.
- **The signed mode** — a second mode signs the operator in and exchanges one application for its signed credential. Login resolves the mounted IAM session first (`ctx.iam` access/auth tokens plus account id), then the DSH-home settings section's remembered login for the project (`ui-sdkwork-access-token` → `accounts[project]`), then the typed form; the password grant presents the public bootstrap token as the credential-entry `Access-Token`. The Host half owns the standard settings section and projects it atomically to `<DSH_HOME>/sdkwork/access-token.config.json` (mode `0600`); the browser reads and writes the section through `ctx.configForms`. An `admin`/`operator` login is upserted into that section (idempotent); ordinary accounts are never persisted. The deploy application list is filtered to applications the signed-in user created or solely owns, the exchange re-checks that ownership, and the response is decoded and validated (not `alg:none`, `app_id`/`aud` equal the anchor, release scope matches the installation, a `USER` release names the session user, tenant match, one-hour lifetime class, unexpired `expiresAt`) before the credential is shown. The signed credential is session-class and is never written into a committed profile file.

## Alternatives considered

| Rejected | One-line reason |
|---|---|
| Spawn `materialize-client-env.mjs` from a new Host Remote | That tool materializes URLs and bindings from `etc/topology`; the requested action is one project's token matrix, and a Host process would duplicate the identity resolution the manifest already carries |
| Write the token files from the browser without the directory bridge | The plugin would need its own RPC and lose the governed text bound, parent-directory rules, and cancellation the bridge already owns |
| Replace the whole profile file from the token values | It would drop the URLs and bindings the profile file also carries; the merge keeps every foreign key |
| Let the row appear for every project directory | The token belongs to a manifest-bearing SDKWork application root; a non-SDKWork project would only reach the empty state |
| Hard-code the application type from the manifest only | A uni-app root, a Vite root with a silent manifest, and a Harmony template disagree between manifest and files, so detection also reads the root's markers and the dialog lets the operator override it |
| Skip authentication and let the dialog mint a long-lived signed token | Forging a signed application credential client-side would bypass IAM's ownership entitlement and revocation; only the §8 exchange may issue one, and only to the signed-in user's own applications |
| Commit the exchanged signed token into `SDKWORK_ACCESS_TOKEN` | That carrier is the public `alg:none` isolation token accepted on credential-entry routes; a signed session credential is rejected there and must never be committed (one-hour TTL, revocable) |
| Persist every login, or ask the user to re-enter privileged credentials each run | Only admin/operator service accounts are remembered, in the standard settings section persisted under the harness home and projected to `<DSH_HOME>/sdkwork/access-token.config.json` (`0600`); an ordinary user's password is never written, and the save is idempotent with a visible notice |

## Consequences

Right-clicking a `sdkwork-*` project in the workspace browser offers **初始化 Access Token**. The dialog has two modes. The public mode discovers the application roots, defaults the token level from a manifest organization binding, lets the operator choose the level (tenant-level or organization-level, with the organization id), the application type and runtime target per root, and the profile subset, previews the isolation claims, and initializes the matrix. The signed mode reuses the mounted IAM session or signs in with the configured/typed account, lists only the applications that user created, exchanges the selected one for its signed credential, and shows it with copy actions. The result list reports every written, unchanged, or failed file.

The repository-level materializer remains the canonical full-materialization owner: this initializer writes only `SDKWORK_ACCESS_TOKEN` (plus the Harmony template's profile identity keys), so a declaration that pins a deployment anchor stays the source for its own runs; the dialog can take that anchor as an override. The signed credential is the opposite kind of material: issued by IAM, effective for about one hour, revocable, and deliberately kept out of the committed matrix.

Verification lives in `tests/`: `access-token.client.spec.ts` (canonical bytes and fail-closed scope rules), `application-types.client.spec.ts` (format table, detection, Host-path joins), `project.client.spec.ts` (root discovery and manifest identity), `initializer.client.spec.ts` (merge strategies, directory creation, idempotency, per-file failures), `access-token-settings.client.spec.ts` (project keys, lookup/upsert, projection document, page-global decode), `access-token-host.client.spec.ts` (DSH-home target, section schema, atomic writer, commit rewrite, failed-write logging), `signed-token.client.spec.ts` (privileged-account detection, ownership filter, credential validation), `sdkwork-iam-port.client.spec.ts` (the real SDK transport: login/list/exchange routes, headers, bodies, envelope), `access-token-dialog.client.spec.tsx` (public-mode discovery, level choice, initialization, empty/unavailable states, settings-face save), `signed-token-panel.client.spec.tsx` (auto/manual login, privileged save, own-application list, exchange, validation failure), and `apply.client.spec.ts` (service, overlay, context-menu contribution, IAM session wiring, settings read/write, teardown). The row-menus suite adds the row's presence conditions and dispatch.

The project menu action pattern follows the publish entry of [Project publish and canonical app linkage](2026-10-23-project-publish-entry-and-canonical-app-linkage.md): the menu row carries only the clicked directory, and the owning plugin provides the flow behind an injected service.
