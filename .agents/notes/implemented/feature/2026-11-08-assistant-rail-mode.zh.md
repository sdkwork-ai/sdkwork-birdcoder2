# Agent Note：把 Bot 团队做成首页下方的模式栏条目

Status: implemented

[English](2026-11-08-assistant-rail-mode.md) | 中文

## 问题

Bot 团队（`ds-bot`）可以被装进本分叉，却无法随分叉出厂，其表面也没有自己的导航入口。
DS Bot 是外壳换肤：在 Bot 模式下，它的浏览器半边遮蔽框架当前会话的侧边栏与对话单元格，
而且只有它自己的 store 能写这个表面偏好——它自带的「返回 DSH」控件是唯一的退路。因此出厂
构建里没有「助理」条目；只安装插件则模式栏毫无变化，底下却多了一个由插件私有的表面偏好。

插件也无法自己提供这个条目：`ui-sdkwork-app-modes` 用封闭词表（`CUSTOMIZABLE_MODES`）
过滤已注册的 key，`ui-layout` 的 `AppModeId` 联合类型决定中栏如何渲染。词表之外的条目永远
不会渲染。

## 决策

Bot 团队作为一等应用模式出厂：子模块 `plugins/sdkwork-dsh-bot`、web-app 补丁中的一行
`sdkwork-bot`、框架词表中紧邻 `code` 之下的新 `assistant` 模式，以及一个本分叉自有的模式栏
包（`packages/client/ui-sdkwork-assistant`），由它拥有「助理」条目并把它与插件的表面绑定。

### 组合

`packages/bundle/web-app/cordis.patch.yml` 带两行：`ui-sdkwork-assistant`（模式栏条目与
绑定）与 `sdkwork-bot`（`name: ds-bot`）。插件自带的 `dsh.bundle.patch` 刻意不加进 profile
的 bundle 列表——这一行就是唯一挂载点；它的 `web-search-auto` 行也不带：profile 配置的搜索
提供方仍然是权威，Bot 团队的 `web_search` 和其它表面一样使用它。

### `assistant` 是外壳模式，不是页面

`AppModeId` 增加 `assistant`，`AppFrame` 把它当作与 `code` 并列的外壳模式：中栏保留 `main`
面板（会话），左栏保持可见（Bot 团队的侧边栏就在那里），右栏保留轨道，会话标题继续占用窗口
标题。若做成 keyed 的 `mode.page` 页面，则会隐藏侧边栏——正是 Bot 团队要绘制的那一列——
也无法容纳一个「对会话换肤而不是并列页面」的表面。

`ui-sdkwork-app-modes` 把 `assistant` 加进 `MODE_ORDER`（紧随 `code`）与 `FIXED_MODES`，
因此出厂布局显示它，自定义弹窗无法隐藏它。词表条目无条件存在；*座位*只在模式栏包被组合时
存在。去掉插件的部署既没有座位也没有弹窗行。

### 表面接缝

上游只通过自己的控件暴露表面，所以插件新增一个公开扩展点：`ctx.botSurface`，一个持有
`bot` 或 `agent` 的可观察来源，加上一个执行与所有内部控件同一动作的 `set(mode)`。模式栏包
以可选注入方式使用它；服务缺席时该包不贡献条目、也不强制任何表面，因此未组合插件的组合既
不会出现点不动的图标，也不会把框架困在无法退出的表面上。

该包用幂等写入双向协调：「助理」模式要 Bot 表面，其它模式要智能体表面，而表面变化写回对应
模式。无论用户从哪一侧操作，两者都在一步内收敛——模式栏，或插件自带的返回控件。挂载时框架
处于首页，因此插件挂载的同一步就收起上次记住的 Bot 表面；「助理」是明确选择，而不是落地态。

接缝的另一半是 `ctx.layout.mode`：layout 服务现在把模式栏选中态作为可订阅来源与 `panelInfo`
并列发布，表面插件因此可以跟随模式栏，而不必持有模式栏的 store 或读框架 DOM。

### 插件改动及其构建

对子模块的唯一改动就是 `ctx.botSurface`：它位于插件仓库的
`feat/assistant-rail-surface` 分支（`ds-bot/src/client/index.js`，提交
`79bc7b0`），其已提交产物（`ds-bot/client.js`）用插件自己的构建重建。该分支已推送，
CI 检出可以解析这个 gitlink；把它合入分叉仓库的 `main` 并升级 pin 是发布步骤。该改动
不含模式栏或「助理」词汇，因此可以原样上游给 DS Bot。

产物用平坦的 `npm ci` 安装构建，而不是工作区的 pnpm 布局：bundle 带有由模块路径派生的
source-region 注释，pnpm store 布局会重写数千行注释而代码完全不变。`plugins/README.md`
记录了该流程。

## 考虑过的替代方案

**做一个绘制 Bot 团队的 keyed `mode.page` 页面**——Bot 团队不是页面。它的侧边栏、对话
单元格与输入区都是框架已在显示的会话的被遮蔽 slot；把页面放在会话旁边只会得到一个空中栏和
隐藏的侧边栏，而它需要的每个 slot 都只能在这里重新实现。

**从模式栏条目写插件的 `localStorage` 偏好**——该键只在插件挂载时读一次，插件订阅的是自己
的 store 而非 `storage` 事件。写入要等到重载才可见，且插件自带的返回控件在此期间与模式栏
不一致。

**把条目做成 `mode.rail.panel` 快捷入口**——该席位是设置上方的底部簇。需求位置是首页正下方、
顶部组之内，而该组只渲染模式条目。

**在插件里硬编码模式 id**——插件将学会分叉专有词表与模式栏假设。服务接缝让插件保持通用：
宿主要么注入 `ctx.botSurface`，要么不注入。

**由 `ui-sdkwork-app-modes` 拥有条目**——图标会在每个部署中出现（包括没有 Bot 插件的），并
选中一个表面不存在的模式。归属应落在能同时按服务门控的包上。

## 后果

出厂构建现在把 Bot 团队作为首页正下方的「助理」条目提供，Bot 数据仍在 `$DSH_HOME` 之下。
两个表面都有模式栏入口，任一表面自己的控件都会带动另一个。

代价是与第三方产物之间的软契约，外加一个分叉本地的插件提交：`ctx.botSurface` 改名会让
bundle 验收用例失败（在那之前则静默隐藏条目）；子模块现在带有一个在上游尚不存在的提交。
本仓库「`plugins/*` 只读」的规则因此为一个增量且通用的服务破例；本笔记与
`plugins/README.md` 记录在案，未来的 pin 升级必须保留该服务，或同时更新两侧。

Bot 团队默认处于收起状态，想让它是落地表面的部署应改框架的默认模式，而不是这个包。条目在
模式栏中是固定的：不想保留它的用户只能去掉插件行。Bot 模式下插件自己的固定左列会覆盖框架
左缘，因此助理表面激活时看不到模式栏；回到智能体表面后模式栏恢复（走插件设置里的切换控件）。

在条目出现之前写成的布局原本会把它显示在模式栏末尾，因为 layout store 会把存储顺序里缺失的
模式追加到末尾。出厂顺序版本号（`dsh.railLayoutOrderRevision`，`RAIL_ORDER_REVISION`）会
一次性把它移到首页正下方；此后用户的重新排序会保留下来。
