# Agent Note: one cloud expert catalog for the Experts tab

Status: implemented

English | [中文](2026-11-28-expert-market-one-cloud-catalog.zh.md)

## Problem

The Experts tab answered "which expert do I use" twice. One chip embedded the SDKWork App Store's expert catalog page; the other embedded the built-in expert package's own roster panel. The two showed the same 331-expert roster from two sources — an app-store database and the package's bundled assets — with different filters, different card anatomy and different actions, so a person had to guess which one held the expert they wanted. The reference design the product asked for (a curated shelf over a five-column card grid, 专家 / 专家团 in one page, a sort control, division chips, per-expert usage statistics) existed in neither view: the package deliberately refused to fabricate the collections and statistics, because the catalog the database owned did not carry them.

## Decision

The tab has one view. `@deepseek-ai/dsh-client-ui-sdkwork-markets` draws it (`ExpertsCatalogPage`), and it reads the SDKWork Agents expert catalog: `expert_divisions`, `experts`, `expert_teams` and the new `expert_collections`. The retired chips, their strip and the embedded App Store page are gone, together with the panel-ledger plumbing (`expertMarketPanel.ts`, `ExpertMarketSurface.tsx`) that existed only to draw the package's panel in place.

The data the reference design needs is now database-owned rather than client-invented. `sdkwork-agents` gains migration `0011_expert_market` — `ai_expert_profile` (curated usage count, badge, catalog order, publish time), `ai_expert_collection` and `ai_expert_collection_item` — seeded from `database/seeds/common/004_expert_market.sql` for all 331 experts and six featured collections, exposed by `GET /app/v3/api/ai/expert_collections` and by four added fields on the expert list, and carried into the generated TypeScript and Flutter App SDKs. One expert is still one managed agent and a team is still several of them; the page renders both kinds from that one catalog.

The seam between the two packages is unchanged where behavior lives. `@deepseek-ai/dsh-client-ui-sdkwork-experts` keeps the `@` picker, the six summon tools, the team engine, the settings page and its `main` panel; the market page suppresses that panel's sidebar row because the tab is the expert navigation entry, and the panel key stays the one string the two packages share. Card actions reach the package's `agencyAgents` Remote: "use" enables the expert (or team) first and then starts a conversation whose mention text is the package's own reference format, so a conversation opened from the market reads like one opened from the picker. The catalog data-plane trigger that pushes the roster, teams and both persona locales into that Remote overlay stays, so the tools serve what the tab shows.

Two catalog details are owned at that seam rather than in the page. An expert's `tags` are its subject tags: the read model drops the managed-agent vocabulary (`expert`, `conversation`, `official`, `commercial`) and the division code, and the card falls back to the division's display name when a deployment seeds no subject tags, so the card never shows record vocabulary as if it described the expert. A collection payload localizes its `name`/`description` and each member label to the requested locale, the way the team payload does, while its `…En` fields stay available. A team payload carries the whole runnable definition: its goal, its **shared constraints**, its delivery requirement, its examples and its ordered members, because the package's team runtime builds the coordinator prompt and each member's brief from exactly those fields; the catalog authors the constraints once, so both locales serve the same text. The catalog's `name`/`description` come from the single `ai_agent.display_name` column, so the last locale seed applied wins; a Chinese profile therefore seeds `zh-CN` last, and both locale persona sets stay required because the catalog verification asserts 662 persona rows.

## Alternatives considered

- **Keep both chips and restyle only the market panel.** Two sources would still disagree, and the panel's virtualized two-column grid hard-codes card geometry (`EXPERT_CARD_HEIGHT`) that the reference five-column grid cannot reuse without rewriting the windowing. One page over one catalog removes the divergence instead of hiding it.
- **Draw the reference layout inside the expert package.** The package is the capability owner, not the market surface; the market owns the page chrome, the header search and the cloud gate. Putting the gallery there would have inverted that ownership and made the package depend on the market's gateway binding.
- **Keep the App Store embed for experts and swap its data source.** The embed is another application's page; it cannot read this repository's catalog without a wire contract, and its cards carry app-store fields the expert catalog does not own.
- **Derive usage statistics client-side.** The reference numbers are editorial display data, not telemetry. Deriving them in the browser would present a guess as a fact; the catalog now carries them as seeded, versioned data.
- **Fail the whole catalog when the collections endpoint is missing.** `expert_collections` is the newest surface, so a deployment whose Agents build predates it answers 404. That costs only the featured shelf; the roster still loads.

## Consequences

- The Experts tab has no sub-tab state, one search field and one gate: the cloud catalog, the shared sign-in face, or the unconfigured notice. `packages/bundle/web-app/tests/built-in-expert-market.spec.ts` still pins the package, its `main` panel key and the two composed rows.
- The team definition now matches the package's team contract: `0013` adds `coordinator_prompt`, so a custom coordinator is representable — required when `coordinator_mode = 'custom'` and empty for a template — and `constraints_text` is capped at 2000 characters instead of 4000. `constraints` and `coordinatorPrompt` are served on the team payload, so the package's team runtime receives the text it builds the coordinator brief from. The shipped verification script still fails closed on either bound, so a later baseline change cannot quietly reintroduce a team the app rejects at ingest.
- The Expert tab renders an expert's emoji tile rather than the reference's illustrated portrait, because the portrait pool lives inside the expert package and a feature plugin may not import another feature plugin's values. The tile carries a stable decorative tint derived from the division.
- A deployment must carry both changes: the tab reads `expert_collections` and the expert profile fields, so a client-only rollout shows the roster without its shelf and statistics.
- Verification: the package's component spec covers the shelf, both views, the three sorts, the facets, the detail dialogs and the failure and empty states (`packages/client/ui-sdkwork-markets/tests/experts-catalog-page.client.spec.tsx`); the page-level spec covers the merged tab and the use actions; `apps/web/tests/expert-market-gallery.e2e.ts` asserts in a real chromium that the retired chips and strip are gone and that the tab always draws an actionable face. The data plane is covered by the Rust unit tests, `pnpm check:expert-catalog`, the contract suites and the regenerated SDK build. The wire contract is mounted, not inferred: `http::expert_catalog_http_tests` drives the real combined route tree through `tower::oneshot` and asserts the response envelope, pagination, the profile fields, per-locale collection payloads, the division filter and the missing-expert `404` for all four endpoints. The deployment path was exercised from an empty schema on the local development database: `db:migrate` applied the baseline plus `0011`, `db:seed` applied the profile's six scripts, `db:status` reports clean, and the shipped `database/verification/expert_catalog_checks.sql` passes for one seeded locale (331 experts, 22 divisions, 5 teams, 15 members, 331 personas, 331 profiles, 6 collections, 18 items, no dangling reference) and for two (662 personas). The store's list queries reproduce 22 / 331 / 5 / 6 against the seeded rows. The standalone agents gateway also boots against that database and its startup drift gate validates the 39-table contract; a process-level HTTP run is not part of the evidence, because the gateway stops on deployment wiring unrelated to this catalog (a missing audit emitter and CORS allow-list in the production posture, a duplicate `/healthz` registration in the development posture).
- The seed gate needed a framework fix to reach that state: `sdkwork-database`'s seed scanner masked string literals line by line, so the prose a multi-line persona literal carries (`GRANT`, `EXECUTE(`, `--`) was read as SQL and every seed that embeds a persona was rejected. The scanner now blanks literal bodies — single, double and dollar-quoted, across newlines — before the keyword and injection scans; real statements and trailing comments are still rejected.
- Not yet owned by the catalog: subject tags for the 331 experts. Until a deployment seeds them, every card shows its division as the subject chip; seeding them is a catalog data change, not a page change.
- A team's detail dialog states its goal, shared constraints, delivery requirement and members, and an expert's dialog names its division the way the chip rail does. Earlier those two dialogs carried the constraint nowhere (the catalog read model dropped it) and printed the raw division code.
