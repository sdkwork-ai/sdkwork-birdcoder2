# Agent Note：插件 tab 里的插件市场

Status: implemented

[English](2026-10-31-plugin-market-subtab.md) | 中文

## 问题

fork 的 `markets` 模式页面替换了上游的插件页（见[替换规则](../architecture/2026-09-06-sdkwork-markets-public-mode.zh.md)），因此从侧边栏 `插件·专家·技能·链接器` 进入的页面没有 `plugins.tab` 座位。社区插件市场——`dshmarket` 插件包——恰好注册在上游那个座位上（以及设置里），于是在本组合里它只出现在设置背后，不在插件表面本身。

产品需要让市场打头：第一个 chip、排在应用自己的云端目录之前；未安装时也能被发现；装好之后能自行更新，而本仓内包不锁定它的版本。

## 决策

### 打头的子 tab 承载市场自己的页面

`ui-sdkwork-markets` 新增第四个插件子 tab `market`，并排在第一位：`[插件市场 · 云端目录] | [官方插件 · 已安装]`。原有细分割线改为只出现在 `official` 之前，让两个市场视图读作一组。插件市场同时是**落地视图**：打开插件页就落在用户真正想要的那个目录上，每次重新进入（切换分类、从「我的专家」返回）也回到那里。云端目录因此不再承担默认表面、进入时无需拉取；市场的挂载会拉取社区目录，这是主推视图被接受的代价。

这里不重画面板。`dshmarket` 早就为「宿主把它的面板渲染进自己的容器」发布了 `market` 客户端服务（`render({ surface: 'plugins' })`，契约版本 1），这正是上游外壳为第三方宿主加的扩展点。本页面：

- 把该服务作为**可选**依赖消费（`ctx.inject(['market'], …)`），并通过一个小型可观察账本（`marketPanel.ts`）发布出去，因此页面挂载之后才加载的插件依然能接上，卸载时面板随之撤下；
- 把返回的元素渲染在 chip 行下方带滚动的视口里；该 chip 激活时只收起页面自己的搜索框（市场页面自带搜索、分类、安装弹窗、更新、备份与诊断，旁边再放一个失效的搜索框只会读作坏掉），**保留页头的「添加」菜单**（创建插件 / 添加插件市场），让页面自己的创建流程仍然可达；
- 只认版本 `version === 1` 且带 `render` 函数的契约。将来改版时降级到下面的入口面，而不是让页面崩掉。

### 四种状态，由插件 store 判定

没有发布控制服务时，chip 依然渲染——只在安装后才出现的市场等于发现不了。具体界面由插件 store 的读取结果决定：

- **加载中** —— 首次清单读取进行中（这次读取由这个门自己发起，因为市场 chip 可能是启动后最先看到的表面）；
- **失败** —— 读取失败，带重试；
- **待加载** —— 插件包已安装，但它的浏览器半边不在这次页面加载里，刷新页面即可加载；
- **已停用** —— 插件包已安装但未被选中（例如在「已安装」里被停用），刷新永远不会加载它，因此把人送到开关处；
- **未安装** —— 安装入口，走与本地插件视图相同的流水线（先 `store.openInstall('dshmarket')`，再走 store 唯一的 Install 动作），另外给一条去云端目录的路。

store 报告部署不管理插件时，安装按钮永远不会可用，而是给出原因。安装弹窗挂在页面层级、面板旁边，因此进度、日志、取消与重启提示不会随面板切换而消失。

### 安装与更新是插件包自己的事

市场是一个 profile 插件包，走普通插件流水线安装（`dsh plugin --profile <name> add dshmarket`，或应用内插件管理器），后者把插件包选进 `dsh.profile.bundles` 并应用它自己的 `cordis.patch.yml`。本包不声明版本、不声明依赖、也不写更新逻辑：市场通过自己的卡片与发布通道更新，仓内页面只观察结果。因此托管 tab 能跨市场版本继续工作。

## 考虑过的替代方案

**用新 slot 代替服务。** `plugins.market` 座位能让页面不依赖服务契约就渲染市场，但 `dshmarket` 不会往那里注册，而没有注册方的 slot 什么也不渲染——那需要改第三方包，并新增一个没有其他消费者的 slot。服务才是那个包已经为这类宿主发布的契约。

**保留云端目录作落地视图。** 这样能延续页面原来的进入表面，也不必在每次访问时拉取社区目录。产品选择了市场：这个 tab 的意义就是让市场成为第一眼看到的东西，把落地视图留给云端等于把它藏在一个 chip 之后。拉取代价被接受，安装/空状态界面保证在未装市场的部署上这个入口仍然有用。

**把 `dshmarket` vendor/fork 进本仓库。** 那样可以随意改面板，代价是切断市场自己的更新路径——与需求相反。通过 profile 安装才能让更新持续流入。

**用上游页面的 owner props 接管安装。** 上游的 `plugins.tab` 会给注册方宿主的 `install` 与 `openPackage`；本组合没有声明那个 slot，而市场刻意自带安装界面，因为走宿主会丢掉市场的进度、任务列表与取消。

## 后果

页面与市场之间只共享一个契约（`market` 服务，版本 1）与一个事实（`dshmarket` 是否在 store 的插件包列表里）。市场发布改动渲染契约时，代价是实时面板，本页面回退到安装/待加载界面，直到追上为止；保持契约的市场发版则不需要本页改动。进入该 chip 时才会发起门的清单读取（store 会合并并发读取）；由于这个 chip 就是落地视图，该读取会在每次进入插件页时发生，市场自己的目录拉取则随实时面板挂载发生。

市场的设置分区与 `plugins.bundle.config` 卡片仍在那些座位存在的地方渲染，因此尚未加载本页新 bundle 的部署，刷新后仍可从设置进入市场——两扇门并存。

## 验证

`pnpm exec vitest run packages/client/ui-sdkwork-markets/tests/markets-page.client.spec.tsx packages/client/ui-sdkwork-markets/tests/market-panel.client.spec.ts` 覆盖子 tab 顺序与分割线、实时面板的 `render` 调用、「添加」菜单在插件市场上仍可用且「创建插件」能派发、安装入口的 store 调用（含忙碌态）、待加载/刷新、已停用与不可管理界面、加载中与失败界面，以及可选服务的 attach/detach 账本。客户端 bundle 用 `pnpm --filter @deepseek-ai/dsh-client-ui-sdkwork-markets bundle` 构建。

端到端：一个装有 `dshmarket` 的临时 profile 由 `dsh web` 提供，并通过 Chrome DevTools Protocol 驱动。插件页显示 `插件市场 | 云端目录 | 官方插件 | 已安装`，选中第一个 chip 后渲染出市场自己的面板——标题 `插件市场`、版本 `v1.73.5`、发现/主题/收藏/已安装/已屏蔽/高级/任务 tab，以及已加载的社区目录（`全部 (7.9k)`）。集成没有产生控制台错误。同一探针对 `dshmarket@1.73.6`（运行中桌面 profile 安装的版本）也渲染出相同面板并显示 `v1.73.6`，该宿主 `/dsh-market/status` 返回 `version` 与 `installed`。运行中的桌面应用已把市场作为 profile 插件包装好，因此这个 bundle 重新构建进应用后，市场也会出现在那里。
