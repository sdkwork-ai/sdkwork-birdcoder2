# Agent Note: 尚未支持的文档格式与各自的代价

Status: proposed

[English](2026-09-11-document-preview-format-matrix.md) | 中文

## Problem

七个预览已共用一套地基落地——PowerPoint、Word、Excel、PDF、图片、视频与音频——覆盖了 已落地的 Agent Note《SDKWork 文档预览共用一套 OOXML 地基》。读者仍然可能打开一个本分支不渲染的文件，并收到最初触发这项工作的「非文本文件」提示。

决定接下来做什么，需要两样这棵树没有记录的东西：还剩哪些格式，以及每一种究竟要花多少代价。「支持整个 Office」不是计划，因为剩下的格式并不是已落地格式的变体。`.xlsx` 与 `.xls` 的差别，等同于 ZIP 格式与九十年代复合文件记录格式的差别；`.ods` 与 OOXML 共用容器却不共用任何 schema；`.pst` 是邮箱数据库，而不是文档。

距离「可商业化」也不是一个单一的差距。有两个独立变动的因素：**保真度**，指渲染器画出多少内容之后读者才会察觉缺失；以及**覆盖率**，指真实用户打开的文件里有多少能被渲染。七个已落地的预览在各自包的 README 中如实说明了两者，本note 将其延续下去。

## Proposal

### 格式矩阵

Office 家族中每一种尚未支持的格式，以及各自所需的工作与所处档位的原因。

**A 档 —— 同一套地基，换一套 schema（每种以周计）。**

| 格式 | 容器 | 工作 |
| :-- | :-- | :-- |
| `.odt`、`.ods`、`.odp` | ODF：与 OOXML 同样是的 ZIP + XML | 不同的样式模型（自动样式与命名样式、`style:family` 而非 `p:sp`/`w:p`）、不同的编号模型，以及用于标签的 `meta.xml`。容器、关系与主题读取已经是共享的。 |
| `.vsdx` | ZIP + XML | 页面与形状模型，带主控/实例之分。没有文本 run 级联，因此比 WordprocessingML 更小。 |
| `.xlsb` | ZIP，但记录是二进制 | 容器已经能读；工作表、样式与字符串表是 BIFF12 记录而非 XML。是在已有几何之上新增一个解析器。 |

**B 档 —— 每种格式一个独立的二进制解析器（各自是一个项目，需逐个做取舍决策）。**

| 格式 | 为什么它不是变体 |
| :-- | :-- |
| `.doc`、`.xls`、`.ppt` | 装着 1997 年二进制记录格式的 OLE2 复合文件。每一种都是独立规范：Word 的二进制表流与分片表、BIFF8 工作簿、PowerPoint 记录流。共享地基在容器层之下完全不适用。 |
| `.vsd`、`.pub`、`.one`、`.mpp` | 同类问题换了一个产品，且可用于校验解析器的公开工具更少。 |
| `.rtf` | 基于文本，因此没有容器工作，但有它自己的控制字语法与自己的排版模型。 |
| APE、DSD、WMA、AMR 音频；WMV、AVI 视频 | 目前只解释、不绘制。要播放它们需要的是解码器而不是解析器：没有一个是容器问题。 |

**C 档 —— 不是渲染问题。**

| 格式 | 为什么不属于预览的范畴 |
| :-- | :-- |
| `.pst`、`.ost`、`.msg` | 邮箱存储与邮件文件。有用的功能是架在数据库之上的邮件阅读器，而不是页面渲染器。 |
| `.accdb`、`.mdb` | 数据库引擎与查询界面。 |

### 「可商业化」还需要什么

除了新格式之外，已落地的预览在撑得住商业用户之前还需要一些工作。按读者最先察觉的顺序：

1. **Word 分页。** 渲染器按整块装箱，从不把段落或表格拆到下一页，且其测量路径只在降级模式下被跑过。一个与 Word 断页方式不同的分页文字处理器，是本家族最显眼的保真缺口。
2. **Excel 虚拟化与公式显示。** 网格会挂载每一个填充行，条件格式也未求值。
3. **PowerPoint 图表与 SmartArt 覆盖。** 目前两者都画成带说明的占位符。
4. **音频波形图。** 进度条只是普通滑杆；解码出的波形才是读者用来定位的东西。
5. **PDF 批注与加密文件。** 表单控件与批注外观不会合成，也没有密码输入。
6. **视频字幕与轨道选择。**
7. **共享视图外壳。** 主体生命周期在七个组件中重复，并让 `pnpm run duplication` 持续为红。
8. **视觉回归语料。** 各解析器已用真实编码器的输出验证，但没有任何东西把渲染结果与 Word、Excel、PowerPoint 对同一文件的输出做比对。
9. **对抗性输入。** 没有任何预览做过模糊测试。OOXML 解析器要遍历攻击者可控的结构，而目前只喂过格式良好的文件。

### 建议顺序

1. **共享视图外壳**，因为之后的每一次改动都要动这七个组件，而重复度是这棵树唯一为红的质量信号。
2. **已落地部分内部的保真缺口** —— 先 Word 分页，再 Excel 网格，再 PowerPoint 图表占位 —— 因为它们影响用户已经在打开的文件。
3. **A 档格式**，按 `.ods`/`.odt`/`.odp`、再 `.xlsb`、再 `.vsdx` 的顺序，因为每一种都能复用整套地基，而 ODF 三者共用同一个 schema 家族。
4. **在任何 B 档格式之前先建立视觉回归语料**，因为没有参照输出的二进制格式解析器无法判定其正确性。

B 档是代价不再可预测的地方。`.doc`、`.xls` 与 `.ppt` 各自的体量与 A、B 两档之和相当，需要来自真实 Office 版本的样本，且无法仅凭规范判定正确性。它们应当被逐个决定，先对单一格式做出取舍，再谈下一个。

## Acceptance criteria

每一步都以无需阅读实现即可验证为准：

1. **共享视图外壳** —— 七个预览主体组合同一个外壳组件，`pnpm run duplication` 报告它们之间没有克隆，且所有既有预览测试无需改动仍通过。
2. **Word 分页** —— 对一批真实文档语料，跨页边界的块与 Word 在相同位置断页，且测量路径在真实浏览器中运行，而不再只跑降级模式。
3. **Excel 虚拟化** —— 拥有数万填充行的工作表在滚动时不挂载每一行，且网格仍渲染同样的单元格。
4. **一种 ODF 格式** —— 新预览能识别容器、读取标签、渲染其文本与样式，并有基于 LibreOffice 产出文件的测试。
5. **视觉回归语料** —— 每种已落地格式都有一个样本，其渲染页面与对应 Office 应用产出的参照输出比对，并有成文容差。

## Risks

**二进制格式的收益可能低于代价。** B 档的解析器无法仅凭规范验证，而对 `.doc` 的部分渲染，可能不如该格式今天得到的那条准确的转换提示对读者有用。这正是它们各自单独取舍、而不作为阶段推进的原因。

**保真缺口可能吞掉全部价值。** 一个断页方式与 Word 不同的 Word 预览，对任何需要比对输出的人来说都不如没有预览。因此计划把已有格式排在新增格式之前，把视觉语料排在一切 B 档工作之前。

**地基未必能延伸到 ODF。** 共享库脱胎于三种 OOXML 格式；ODF 共用容器与关系图，但样式与编号模型不同。若共享层适配 ODF 效果不佳，诚实的做法是再建一个小库，而不是把抽象加宽到同时覆盖两者。

**语料会成为维护负担。** Office 应用的参照输出必须随样本变化而重新生成，且只在产出它的平台上才有意义。

## Alternatives considered

**按扩展名顺序实现所有格式。** 扩展名顺序会把 `.doc` 排在 `.docx` 旁边，从而掩盖两者毫无共同点这一事实。它会把预算首先花在最不可预测的工作上。

**画不完美就什么都不认领。** 各预览已经不**绘制**它渲染不了的格式；若不**认领**它们，就会让那些唯一问题只是需要一次转换的文件回到「非文本文件」提示。给出解释严格优于给出错误解释。

**用一个 WASM Office 引擎做通用查看器。** 已在家族 note 中否决：商业许可证、数十兆字节，以及为一个必须在现有标签页内离线工作的预览所需的 `SharedArrayBuffer` 隔离要求。

**在用户提出之前不决定 B 档。** 这是合理的，也正是本note 的建议：分档的意义在于让每个格式的决定都带着可见的代价做出，而不是从「支持 Office」的承诺中推断。

## Consequences

若按本计划推进，这棵树将以独立、可验证的工作单元获得 ODF 与二进制 Office 容器，而已落地的七个预览会在它们已经认领的文件上变得可信。

不做承诺的是：任何时间表，以及任何「预览画得和 Office 一样」的说法。本家族中的每个渲染器都是有明确边界的子集，其缺口都写了下来；第 4 步的视觉回归语料才是把「有边界」变成「有度量」的东西。

本note 不做的决定是 B 档的取舍。每一种都需要自己的 Agent Note、来自真实 Office 输出的样本，以及它自己的答案：对一个 1997 年的二进制格式做部分渲染，对读者而言是否真的比一条准确的「请转换此文件」提示更有价值——而后者正是这些格式今天得到的东西。
