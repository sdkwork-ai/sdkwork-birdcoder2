# Agent Note: 从登录账号获得 BirdCoder 中转模型

Status: proposed

[English](2026-11-12-birdcoder-relay-model-capability.md) | 中文

## Problem

BirdCoder 的模型能力本来就不应要求填写 API Key：登录会话的 SDKWork IAM `authToken` 就是中转凭据，中转的 `GET /v1/models`（OpenAI 兼容的 Cloud Router open API）会返回该账号可路由的模型。有三处缺口破坏了这一承诺。

1. 桌面端用操作系统密钥库加密 `<DSH_HOME>/iam/session.json`，而 Host 运行在无法使用密钥库的子进程里。因此 `@deepseek-ai/dsh-birdcoder-account` 读不到 `authToken`：已登录用户的 BirdCoder 行仍未配置，选择器把每个中转模型标为「需登录」，「模型」页显示 `llm-pi-ai` 的缺少凭据错误。
2. 「模型」页只有一个就绪事实——凭据引用已保存——因此即使账号供给正常，该行也会把登录令牌呈现为用户从未输入过的已保存 API Key，并且无法区分「已登录」与「已存密钥」。
3. 模型发现经由路由凭据执行，失败时只报告 401。登录前，「获取可用模型」没有可用于认证的凭据，也不会像选择器那样发起登录。

## Proposal

**账号供给（已实现）。** 桌面端在提交持久会话时把中转凭据写入 `<DSH_HOME>/iam/relay-session.json`——这份明文兄弟文件只携带 `authToken`，不含 access 或 refresh 令牌——登出时删除，并在启动时为旧版本写入的会话补写。账号插件优先读取该投影，读不到时回退到明文的持久会话，无头写入方因此不受影响。插件通过 `ctx.credentials` 把令牌写入 `BIRDCODER_API_KEY`；用户已保存的值仍然优先，绝不被替换。

**「模型」页中的凭据来源（后续）。** 凭据由账号插件拥有的路由改为呈现账号状态，而不是只写密钥输入框：卡片说明已登录账号、请求使用登录会话，并保留一条明确的「改用 API Key」路径，写入用户密钥后该路由不再由账号供给。就绪事实变为「凭据可以解析」——这正是请求路径本来就在问的问题，而不是「已保存某个值」。删除掩码绝不能在下一轮轮询时被静默重建：用户层配置档记录用户选择了密钥路径，插件在登出前不再为该路由重新开通。

**模型发现（后续）。** 「获取可用模型」解析与请求路径相同的凭据：草稿中键入的密钥，否则就是该路由可解析的凭据（账号令牌或已存密钥）。两者都没有时，它改为打开已挂载的登录界面——即选择器现有的登录闸门——并在 Host 重新发布目录后重试一次，而不是显示 401。返回的列表仍经 `llm/discoverModels` 处理，端点因此仍是相对于随包种子的权威。

**Open API 定义（已在 cloudrouter 实现）。** `GET /v1/models` 与 `GET /v1/models/{model}` 在契约中同时定义两种凭据通道：带 `sk-`/`sp-` 前缀的网关 API Key，或 SDKWork IAM 登录 auth 令牌（可选携带 `Access-Token` 双令牌伴随）。响应中的 `displayName` 与 `vendorDisplayName` 扩展字段属于契约，具体目录路由也用与 chat 相同的分类器接受登录通道，因此每个组合——而不只是生产调用管线——都给出相同答案。

**纯浏览器登录（延后）。** 浏览器页面没有外壳文件。要给它同样的账号供给，需要由客户端 IAM 服务通过 `credentials.set` 推送已提交的会话令牌，并把归属标记迁移到 Host 侧记录，登出时才仍只删除本插件写入的内容。这有意不在本次改动范围内：桌面端才是产品的登录面，纯浏览器用户继续走 API Key 路径。

## Alternatives considered

**只通过外壳投影会话。** 否决：纯浏览器场景没有覆盖，而且投影本身也回答不了「模型」页的问题——解析到的凭据来自账号还是用户。

**把完整会话写成明文并去掉操作系统密钥库。** 否决：refresh 令牌寿命长，本机进程可以读取；而派生投影暴露的恰好是 Host 本来就会以明文写入自身凭据文件的那个 Bearer 值。

**由 Host 通过 IPC 向外壳索取解密后的会话。** 否决：为一个外壳本可以在它已拥有的文件旁用一次原子写入投影出来的凭据，额外引入第二条进程通道、Host 侧服务与生命周期协调。

**新增专用的 `GET /v1/models/available`。** 否决：OpenAI 兼容列表已经是产品调用的契约，客户端也已经在解析它；第二条路径只会重复目录及其分组范围，而不提供任何新信息。

**把凭据来源标记写入凭据记录而不是配置档。** 否决：凭据接缝为所有提供方保存机密，没有产品归属词汇；而账号拥有的路由与用户覆盖之间的区分本来就在配置档里。

## Acceptance criteria

- 全新的桌面端登录、未输入任何 Key 时，BirdCoder 行在一个轮询间隔内变为已配置，选择器把其模型列为可路由（不再出现「需登录」分组）。
- 在该路由上点击「获取可用模型」会返回端点列表并打开选择框；只要会话可用就不会报告 401。
- 用户保存的 API Key 优先于账号令牌，并在登出后保留；登出删除镜像令牌、开通的配置档与中转投影，并恢复此前的默认模型。
- 任何明文文件都不包含 refresh 或 access 令牌；`relay-session.json` 只含 `authToken`、`savedAt` 与版本号。
- 来自没有投影的旧版本的会话，下次启动无需重新登录即可到达 Host。
- cloudrouter 契约同时声明两种凭据通道与模型元数据，并且具体目录路由在 Rust 测试中能认证登录令牌。

## Risks

- **磁盘上的明文 Bearer。** 投影与 Host 凭据文件都以明文保存中转令牌；操作系统密钥库只保护持久会话。缓解：仅属主可读的文件权限、投影不含 refresh 令牌、随会话一起删除。
- **账号拥有凭据带来的意外。** 在配置档记录用户选择之前，编辑掩码的用户仍可能被重新开通；登出路径必须保留用户 Key 及其配置档。
- **部署不一致。** 只接受 API Key 的网关仍会拒绝登录令牌；随包种子保证选择器可用，该限制继续记录在文档中。
